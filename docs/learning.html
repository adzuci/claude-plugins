Reflecting your own work back as a learning plan

The memory vault remembers what you decided. This plugin reads a week of your engineering work and tells you, with evidence, what to practice next.

Part three of a series: start with Memory as reliability practice, then An operating loop for AI-assisted work.

Role lensEngineering manager (SRE background)
Artifactlearning plugin
ScopeLocal sessions or a cloud/web routine

Most retros are about the team. This one is about you. It reads the record of your week, not your memory of it, and hands back three things to practice.

The idea is Harshit Pandey's. He built the first version and argued that a self-retro should cover the work you did, weighted by where your time went, and end in concrete next steps. I have run my own version weekly since May. It is the most useful recurring prompt I have.

A good retro points at one specific thing, cites the evidence, and gives you an exercise.

Two ways to run it

The hard part of a personal retro is data. It lives in two places, and the skill detects which one it can reach:

Local: pull session data directly

  • When your Claude Code session files are present, the retro is built from your own transcripts: how you framed problems, where you pushed back, where you accepted too fast.
  • This is the richest signal. A bundled parser flattens the week's sessions locally, and no GitHub or Jira access is needed.

Cloud: a web routine over your shipped work

  • A scheduled Claude web routine cannot see your local sessions, so it reads what it can: GitHub PRs authored and reviewed, Jira touches, and optionally Glean docs you wrote.
  • This was one of the first web routines I ran. It pairs with an LLM wiki (a git-backed Obsidian vault), so each run commits a durable, reviewable report and DMs it to me on Slack.

If neither is reachable (a cloud run with no vault and no connected accounts), the skill says it needs data and stops. --local or --signals forces a mode.

What running it weekly changed

A learning plan only counts if you do the items. Here is one item from each of four runs and what it became, taken from my session notes:

WeekLearning-plan itemWhat it turned into
Jun 15 Document which invocation surfaces carry ZDR eligibility A ZDR-eligible-surfaces note in the vault's references.md, written before the next infra decision that depended on it
Jun 29 Add failure-mode and rollback notes to skills that write A "Risks & rollback" block added to write-path skills, plus a vault runbook for the native-vs-waterfall enrichment flow
Jul 13 Reconcile MTTR from PagerDuty + BetterStack + the Slack sev channel An MTTR reconciliation step scoped to wire into the create-rca skill, plus a Redis/Sidekiq capacity model
Jul 16 Write up the polling-vs-event-driven trade-off from a live incident A one-page design note comparing cost, failure modes and migration risk. The most valuable item of that run

I shared the Jul 16 run with Harshit. Its third item took an idea I had floated mid-incident and turned it into a design note I could circulate. One item a week worth doing is all I ask of the report.

Design guardrails

The retro is reflective, not punitive: reports may not use the words "gap", "missed", "failed" or "lacking", and every claim must cite a specific session or PR. It is report-only: it generates the plan and, on approval, saves it; it does not touch tickets, memory or code. An empty week or an unreachable signal gets one line saying so, with no padding. The analysis is weighted by where you spent your time (Harshit's original point), so a week that was 90% backend does not produce a report about the 10% that was frontend.

Limitations

The cloud routine depends on the signals it can reach: without GitHub or Jira access it writes a thin report or asks for data. It infers your primary work area from directory and repository paths, which is a guess. Local mode depends on Claude Code's session files being where it expects them. Scheduling works best on the clients I use daily; elsewhere the setup skill gives you the manual command. Like everything here, it is tested mainly on macOS.

How to tell it is working: once a week you get a report that names one thing worth practicing, cites its evidence, and gives you an exercise you could start that afternoon.
