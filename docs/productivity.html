An operating loop for AI-assisted work

A memory layer tells you what you decided. It does not, on its own, move work forward. This is the set of small, inspectable loops I run on top of one Obsidian vault to close that gap, and the design rules that make them safe to trust.

A memory layer on its own is a filing cabinet. It becomes an operating system when small, boring loops move work through it, and when each loop is cheap enough to run without thinking and safe enough to trust without checking.

The memory vault fixed decision loss and surfaced a different problem: the gaps between sessions. A task comes up mid-session and never reaches the backlog. A session gets cleared with uncommitted work still in the tree. Friday arrives and I can't say what the week's AI work actually produced. The vault remembers fine; these are missing loops, not missing memory.

The engineering instinct here is the same one I bring to reliability work: when a manual step keeps failing, you do not try harder, you build a small system with a clear contract. The productivity plugin is that system: a handful of skills that share one vault and one convention, each small enough to read in a few minutes and reason about completely.

Capture is cheap. What is expensive is re-finding the task, the loose end, or the pattern three weeks later.

The loop

The skills form a daily-to-weekly cadence around a single git-backed vault. The vault is the only shared state; every skill reads from it and writes plain Markdown back to it, so any one of them works standalone and none of them depends on another's runtime.

Two skills run in the moment, three on a daily-to-weekly rhythm:

In the moment

  • /todo: capture a durable task in the vault's Kanban backlog.md. Idempotent by design: re-adding an item deduplicates instead of stacking, and an explicit "urgent" promotes the existing item rather than creating a second copy.
  • /wrapup: the pre-/clear preflight. Before you throw away a session, it checks for uncommitted changes, unpushed commits, running jobs, and open obligations, and tells you whether it is actually safe to clear.

Daily and weekly

  • /standup: a daily or weekly status built from Jira, the backlog, and daily reports. The paste-ready block is capped at 90 words and eight bullets; private notes surface the credible five-minute closes.
  • /daily-wrapup, end-of-day review: yesterday's goals, today's outcomes, tomorrow's preview, and a goal commit written back into the vault's session note.
  • /ai-coach: a Friday, report-only review of the week's session notes: repeated friction, capabilities I keep bypassing, and memory candidates. It writes a report and changes nothing.

/productivity-setup ties it together. It installs managed local copies of these skills for every Claude Code and Codex client it detects, records your vault path in ~/.config/adzuci-productivity/config.json, and offers to schedule the Friday coach with whatever scheduler is native to the client you are in. The plugin also ships /budgetclaw-setup for local spend monitoring and an agent-ops pair for privacy-safe scheduled agents.

Contracts, not vibes

The reason I trust these loops enough to run them on autopilot is that each one has an explicit, testable contract. Three examples worth calling out for an engineering audience:

SkillThe contractWhy it holds
/todo Adding the same task twice is a no-op; "urgent" promotes rather than duplicates. A Python helper normalizes bullets, deduplicates case-insensitively, and writes atomically; behavior is pinned by unit tests, not by prompt wording.
/standup The paste-ready block is always under 90 words and eight bullets. A checker script runs against the draft before it is returned; boundary cases (exactly 90 words, exactly eight bullets) are covered in the test suite.
/ai-coach Report-only: it never writes durable memory or mutates a ticket on its own. It requires evidence from multiple sessions before recommending anything, verifies invocations against skills you actually have installed, and stops at proposing.

Design guardrails

The same rules as the memory plugin, because they are the reason the whole thing is safe to leave running:

Everything is plain files. Tasks are Markdown checkboxes in a Kanban board Obsidian renders natively; coach reports are dated Markdown in coaching/. Installs are dry-run first and confirmation-gated: they never overwrite an unmanaged skill of the same name, and every managed copy carries a marker file so updates are safe and removal is obvious. Scheduling uses the client's own scheduler; where there is no good native option, the setup skill hands you the exact manual command instead of quietly writing a cron job. And writes that could compound (task capture, goal commits) are idempotent, so a double-run or a retry never corrupts the board.

What changed in practice

Four months of running this, measured off the vault it writes to:

610
session summaries archived since Mar 16
84
daily notes the loop reads and writes
19
days I closed out with /daily-wrapup

The SessionEnd hook does the archiving, so those 610 summaries cost me nothing to keep, and I stopped deciding what was worth writing down. On the 19 days with something to reconcile I ran /daily-wrapup, and each one means the next morning starts from a written plan instead of a cold read. Tasks moved out of chat scrollback and into the backlog, because capturing one is now cheaper than scrolling to find it. And the Friday coach reads that same pile and, often enough to matter, names a habit I had not clocked. The loops are small; the state compounds.

The practical test: if this is working, tasks stop living in chat scrollback, sessions end clean, and Friday's coach report occasionally surfaces a pattern you would otherwise have missed.

Honest limitations

It assumes the vault convention from the memory plugin: a sessions/ directory of curated notes is what makes the coach useful; without it, weekly mode has little to read. The Kanban layout is an opinion (six fixed sections), not a framework. Scheduling is best-supported on the clients I use daily; elsewhere you get the manual command rather than a background job installed on your behalf. And like everything in this repo, it is tested primarily on macOS; Linux and Windows reports are welcome.

Install the plugin

Add the public marketplace once, install, then run setup.

Claude Code

claude plugin marketplace add adzuci/claude-plugins
claude plugin install productivity@adzuci-plugins
/productivity:productivity-setup

Codex

codex plugin marketplace add adzuci/claude-plugins
codex plugin add productivity@adzuci-plugins
/productivity-setup

Setup asks before it writes anything outside the current project. Pairs best with the memory plugin's vault, but any Obsidian vault works.
