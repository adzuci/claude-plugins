# Harness snapshot

The conversation is not the record; the snapshot on disk is. Read `${CLAUDE_PLUGIN_ROOT}/framework/33-stage-snapshots.md` for why.

**When this runs.** Only inside an explicit harness run: a run id is bound (named in the command, or the
profile's `default_run` with `runs/<run-id>/index.md` under this folder's `.ai/`) and the work is a
harness stage or council lens. A Figma edit, a storyboard update or any other task outside a run writes
no snapshot and publishes no page. If you are unsure, do not write one.

**Storage first** (doc 45 §2). Before any read or write of the record, resolve the mode: a session with no Bash and no Write tool is `notion`; otherwise run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/storage.py" detect` (with `--surface` from the profile's `surface:`, and `--profile <file>` when the profile came from Notion) and print its `say` line once. In `notion` mode every `.ai/<initiative>/...` path in this file names a record page under the initiative's records root (doc 45 §3): write with `storage.py to-notion` and the `notion-create-pages` call it prints, read with `notion-fetch` then `storage.py from-notion`, append ledger events with `storage.py ledger-entry`, and skip git, gh, local `shasum` and `record-sync.sh` (Notion is already shared). In `local` mode the rest of this file applies unchanged; on claude.ai/code, where the profile came from Notion, export `HARNESS_PROFILE=<the fetched profile file>` before any `record-sync.sh` call so team sync sees it (doc 45 §4).

**Repo state (local mode only).** Resolve the repo root first with `git rev-parse --show-toplevel` (doc 43 §10); every `.ai/` path is relative to that root, not to the current subfolder. In `local` mode only: no git repo means the detector already chose `notion` (doc 45 §2); if the profile forces `storage: local` there, say "no-repo mode: storage: local needs a repo; switch to notion or open the repo" and stop, with no git, gh or record-sync call. A repo with no `.ai/` at its root: say "harness not initialised in this repo; run /apollo-product-lab:harness-intake or /apollo-product-lab:product-harness-init" and stop.

## Write mode — `/harness-snapshot write <initiative> <run-id> <stage>`

01. Copy `${CLAUDE_PLUGIN_ROOT}/framework/templates/stage-snapshot.md` to `.ai/<initiative>/runs/<run-id>/<stage>.snapshot.md`. If one exists for this stage, name the new file with a `.<n>` suffix and set `supersedes`.
02. Fill every section from disk, not from memory: run `git status --short`, `git log --oneline -3` per branch, and read the files you cite. Hash each input with `shasum -a 256`.
03. For a build, fix or council stage, fill the **Loop report** line (doc 46 §6) from tool timestamps: minutes for build, tests, mutation, review and fix loops, runs, mutants, review passes, tokens and prompt characters; name any doc 46 breach on the next line and put the line in the stage report too.
04. Checks are rows marked `checked`, `failed`, `unverified` or `not applicable`, with evidence (doc 43 §8). Decisions have alternatives rejected. Open questions have an owner or `unowned`.
05. **Publish the Notion page. Not optional; the write is not done without it.** Under the initiative's `notion_parent` (profile or `harness-manifest.md`), create the page from `${CLAUDE_PLUGIN_ROOT}/framework/templates/notion-page.md` in plain language for a colleague who never saw the chat: decision or finding in the first sentence, options as a table, who decides by when, terms glossed. Before publishing, run the plain-language check (doc 43 §9): a fresh agent that saw no chat reads only the page and states the decision, what follows from it and what the reader must do; rewrite until it can. Where there is no Agent tool (claude.ai chat), run it degraded: re-read only the page text as if new, write the three statements, record the check row as `unverified: degraded plain-language check (same thread)` in the snapshot, and carry that tag into intake reports and council memos; a person, not the model, then confirms the page reads on its own before the gate. End the page with the stamp line `Harness run: <initiative>/<run-id> · artifact: <snapshot file name>` (doc 43 §2.2) and no local paths anywhere on the page. If the stage opened or edited a PR, stamp its body with `Harness run: <initiative>/<run-id>` and verify it with `gh pr view <n> --json body` (doc 20 §8c); an unstamped PR is a `failed` check row. Then write the page URL into the snapshot frontmatter as `notion:` and into the run's `index.md` Notion column. This applies to every `*.snapshot.md`, every `council.*.memo.md`, every `council.*.decision.md` and every gap list; individual lens files (`council.<slug>.<lens>.md`) are machine records and get no page. If no `notion_parent` is recorded, stop and ask for one before reporting the stage; if the Notion connector is not connected in this session, write `notion: blocked: notion connector not connected` and say so in the report, and the next session's first act is to publish it. Never report a stage as written while `notion:` is missing or blocked without saying so in the first line.
06. Append or refresh `runs/<run-id>/index.md`: one row per snapshot (stage, as_of, gate status, path).
07. Append one ledger event, validated by the writer. In notion storage, keep these arguments and let the
    `post-update.py` call below append it to the fetched ledger page; do not append it twice:
    `python3 ${CLAUDE_PLUGIN_ROOT}/framework/ledger/append.py <initiative> --run <run-id> --event <id> --stage <stage> --agent <agent> --model <served model> --outcome <outcome> --evidence <snapshot path> [--tokens N] [--minutes M] [--prompt-chars C]`.
    The writer refuses unknown fields, a bad stage id and a duplicate event id; on an interrupted stage, re-check `index.md` and the ledger before retrying rather than re-appending.
    6b. Order of writes is snapshot → Notion page → index (with the Notion URL in its own column) → ledger. On resume, a snapshot with no index row or a row with no ledger event is repaired in that order and the repair is noted in the snapshot's `Artifacts written`.
08. Run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/post-update.py" --stage <stage> --summary <stage-end-summary> --links <snapshot-and-page-links> --issue <issue-if-given> --initiative <initiative> --run <run-id> --event <stage-event-id> --agent <stage-agent> --outcome <stage-outcome> --profile <profile>` with the values from the ledger event just written, and execute every call in the JSON plan. Copy the Jira issue or `blocked:<reason>` result into the snapshot's `jira:` line when Jira is selected; `both` still executes the Notion call when Jira is blocked.
09. Share the completed record: `bash "${CLAUDE_PLUGIN_ROOT}/scripts/record-sync.sh" push <initiative> "<initiative>: <stage> snapshot"`. The script is a no-op for a solo profile; for `collaboration: team` it commits `.ai/<initiative>`, rebases and pushes (doc 41 §3). Exit 2 means the push did not land: report it, and the stage is not done until it does. Never `--force`.
10. Draft the short stage report in a file, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/verify-claims.py <report.md>`, and add evidence beside every unsupported completion claim. Then report the snapshot path and the three most important rows. Do not restate the snapshot. On a surface without Bash, apply the same evidence rule manually and say the script could not run.

## Read mode — `/harness-snapshot read <initiative> <run-id> [stage]`

1. Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/record-sync.sh" pull <initiative>` first (no-op for solo; for a team profile it rebases so someone else's newer snapshot is what you read). It refuses while `.ai/<initiative>/` has local changes; then read the local copy and say it was not pulled. **Only after the pull**, run the scan mode of `${CLAUDE_PLUGIN_ROOT}/skills/harness-escape/SKILL.md` for this initiative (cheap: stamped PRs updated since the last scan, at most 20) and report the number of new candidates in one line; do not adjudicate them here. Scan changes stay local and are pushed with the next snapshot write. Read `runs/<run-id>/index.md`; open the latest snapshot per stage (or the named stage). Recompute `shasum -a 256` for every listed input and mark each `unchanged` or **`changed since snapshot`**; a decision that rests on a changed input is reported as `in force, input changed` and is not treated as settled. A file listed in the initiative's `unverified-imports.jsonl` (imported from Notion with `--unverified`, doc 45 §3.1) is reported `in force, input unverified` the same way.
2. Read the initiative's `domain/*.md` decision logs.
3. Run `git status --short` and `git log --oneline -3` on each branch the snapshots name.
4. Report: facts established, decisions in force, open questions with owners, gates open, and any conflict between the conversation and disk. The snapshot wins over the conversation; observed reality on disk or at runtime wins over the snapshot, and that discrepancy is written down (errata file in the run) rather than resolved by declaring either side right.

## Hard rules

- Never write a snapshot from an agent's report alone; reconcile against disk first.
- Never edit an older snapshot; supersede it. A council rerun writes `council.<slug>.r2.<lens>.md`, never over the first round.
- Only a change with demonstrated low risk under doc 43 §6 (tests show the output is unchanged and no trigger applies) writes no snapshot; it still writes one ledger event with the commit as evidence. File count does not matter: a one-file index or behaviour change is medium and gets a snapshot. Anything touching constrained copy, consent, a provider, authority or data class is never low.
- Hash prefixes are not hashes: record the full SHA-256; `as_of` is a timestamp, never `now`.
- Never put secrets, tokens, or identifier hashes in a snapshot.
- A missing owner is written as `unowned`, never omitted.
