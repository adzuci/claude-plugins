# Harness council

Read `${CLAUDE_PLUGIN_ROOT}/framework/34-harness-council.md` and `32-model-registry.md` first. The council produces a memo with options; it never approves.

**Repo state (local mode only; in notion mode check that the initiative's records root page exists and has a `harness-manifest.md` record, else point at intake).** Resolve the repo root first with `git rev-parse --show-toplevel` (doc 43 §10); every `.ai/` path is relative to that root, not to the current subfolder. The council needs `.ai/<initiative>/`. In `local` mode with no git repo (only when the profile forces `storage: local`): say "no-repo mode: storage: local needs a repo" and stop. In `notion` mode the initiative is its records root page; for prd and design kinds the council runs without a checkout, while erd, plan and pr kinds need the code and say which lenses are `excerpt-only`. A repo without `.ai/` at its root, or without this initiative: say so and point at `/apollo-product-lab:harness-intake`; write nothing.

**Storage first** (doc 45 §2). Before any read or write of the record, resolve the mode: a session with no Bash and no Write tool is `notion`; otherwise run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/storage.py" detect` (with `--surface` from the profile's `surface:`, and `--profile <file>` when the profile came from Notion) and print its `say` line once. In `notion` mode every `.ai/<initiative>/...` path in this file names a record page under the initiative's records root (doc 45 §3): write with `storage.py to-notion` and the `notion-create-pages` call it prints, read with `notion-fetch` then `storage.py from-notion`, append ledger events with `storage.py ledger-entry`, and skip git, gh, local `shasum` and `record-sync.sh` (Notion is already shared). In `local` mode the rest of this file applies unchanged; on claude.ai/code, where the profile came from Notion, export `HARNESS_PROFILE=<the fetched profile file>` before any `record-sync.sh` call so team sync sees it (doc 45 §4).

**Web surfaces** (doc 45 §5). claude.ai/code: lenses dispatch as usual; no shunt, so step 3b's fallback order picks the adversary and the memo says which route ran. claude.ai chat (uploaded Skills): there is no Agent tool, so run each lens in this thread one after another from its brief alone (re-read only the input record page, not earlier lens output), run the adversary through `glean_default.chat` for prd and design (`independence: unknown`), tag every lens and the memo `degraded: in-thread lenses`, and put "rerun from a Code surface before deciding?" as a human gate on product-size work.

**Designer panel.** When the input comes from a designer intake (`intake.snapshot.md` says `persona: designer`, or the profile does), a design or prd round always includes: research, product (`product-reviewer` competitive and AI-opportunity modes), **reuse** (Fabric components to reuse) and, only when the intake's quick sibling check found the same flow elsewhere in Apollo, the **platform lens** (`product-reviewer` platform mode, doc 47, with one reusable proposal; otherwise its recorded skip row), **engineering feasibility** (doc 34 §2b; for a design-only change the initiative's frontend owner agent, else `frontend-reviewer`, reading the design for build cost, existing components and states it cannot build cheaply; the backend owner joins when the design implies new data or APIs), UX, and the cross-family adversary where one is reachable. The design artifact is the Figma file, Fabric Studio prototype or Claude Design project the designer shared; never ask a designer for a PR or a staging link.

## Steps

01. **Resolve the input and the run.** Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/record-sync.sh" pull <initiative>` before opening anything (no-op for solo; team profiles get the newest shared record, doc 41 §3). `<initiative>` must have `.ai/<initiative>/`; `<kind>` is one of prd, design, erd, plan, pr, verify, decide; `<ref>` is a path, branch, PR number, or URL. The run is `--run <run-id>` if given, else the profile's `default_run`, else the initiative's newest `runs/*/index.md`; if more than one run is plausible, list them and stop before writing anything. Write the input snapshot `runs/<run-id>/council.<slug>.input.md` (doc 33 template) naming the artifact with its full sha. Threshold: only a change with demonstrated low risk under doc 43 §6 (tests show the output is unchanged and no trigger applies) skips the council. File count does not matter: a one-file index or behaviour change is medium and gets the council and the cross-family review. Touching constrained copy, consent, a provider, authority or a data class is never low. Say which rule applied.

02. **Pre-work brief** (doc 34 §2b). After `decide` on this artifact and before the author of the next one starts, write the brief from the roles that will review it (at most five lines per role, from the decided version) into the next stage's input snapshot; skip it when the size rules skip the council. On erd, plan and pr, dispatch the product, design and QA matrix rows as doc 34 §2b says (never `framework-qa-reviewer`, never a code review by `product-reviewer`).

03. **Pick lenses by what the change affects** (doc 34 §2a, doc 43 §5): backend code adds backend; a query, schema or index adds db-perf; a surface owned by a team other than the author's (`surface-owners.yml`, and sensitive files matched with `ApolloDevTeam.team_to_sensitive_files_hash`, run again on the real diff for pr) adds an **owning-team lens** loaded with that team's `platform-rules.md` rows and an owner-disposition row (`approved`, `changed`, `not needed`, who, when). The architecture, backend and db-perf lenses fill one row per applicable `platform-rules.md` rule and, for a change to existing behaviour, check the current behaviour map (doc 43 §4), including that every protection the existing path applies to resolved values is kept. For an enhancement to an existing product, product and UX lenses run only when users will see different behaviour, competitive and AI opportunity become one combined page, and research runs only when the area has no prior research. Then take the kind's defaults from doc 34 §2 and the cross-role matrix of §2b (prd → product, **competitive**, **AI opportunity**, **peer design**, **engineering feasibility**, **UX research**, research, compliance-human, adversary; design → UX, product, **peer design**, **engineering feasibility**, **UX research**, **competitive**, **AI opportunity**, QA, adversary; erd, plan and pr also add product, UX / design and QA as the matrix says; prd and design add the **platform lens** (`product-reviewer` platform mode, doc 47) only when the intake's quick sibling check found the same or a near-same capability elsewhere in Apollo, else the memo carries its recorded skip row, and erd/plan add it for shared-backend rows when the model or service has a sibling backend; erd/plan → architecture, backend, db-perf, **infra** (`infra-lens`, checks the Load model of doc 17 §6.2 against `apollo-infra-patterns.md`; a missing Load model is `failed`, and so is a hook row without host-path numbers (IP18); when Grafana is reachable, query the host peak and the shared resource's peak and put them in the lens brief, else mark them `unverified` and open a pre-merge human check), research, adversary, plus competitive and AI opportunity when the model shape is product-visible; verify → QA, UX; verify runs against the preview of the combined `Need_Preview_Env` PR when one exists, doc 20 §8g). The AI opportunity lens (`product-reviewer`, AI-opportunity mode, doc 42) writes the opportunity table and one now / next version / never question per row; the memo carries those questions verbatim, and after `decide` you append the answered rows to `knowledge/ai-opportunities.md` (template `templates/ai-opportunities.md`) with who decided and why. The platform lens writes the doc 47 table and one platformize now / do locally and record / never question per row; the memo carries them verbatim, after `decide` you append the answered rows to `knowledge/platform-opportunities.md` (template `templates/platform-opportunities.md`), and a cross-team row also needs the owning team's recorded answer before a slice builds it. The competitive lens runs on the Glean family with a Sol second opinion and its output is a competitor-vs-us table with pros, cons, options and a go-ahead question; the memo cannot recommend a build direction without it on a new or changed product. The **pr kind is not dispatched lens by lens**: first check the PR body carries `Harness run: <initiative>/<run-id>` (`gh pr view <n> --json body`; add it per doc 20 §8c if missing); then count its changed files (`gh pr diff <n> --name-only | wc -l`, doc 20 §8b: target 15, over 30 is a `failed` row and the memo's first option is the split, unless a decision record accepts the size; a combined PR from doc 20 §8g is exempt and is not reviewed as a diff); start or reuse its px0 review link (doc 20 §8f) and put it in the report; run the `code-review` supervisor (it owns backend, frontend, security, db-perf, the infra lens for medium and high changes, and the tech-lead synthesizer) and, in parallel with it, `/codex:adversarial-review` as the cross-family adversary and `/apollo-eng:mongo-pr-guard`; on pass 2 both the infra lens and the adversary get only the delta (doc 46 §4); if the PR changes the design (new collection, field, index, job, hook, endpoint or state, or Load model numbers), it is also a design change under step 3a; copy their outputs into `council.<slug>.<lens>.md` files yourself. The **QA lens** for design/verify is the product QA workflow (`feature-qa-wizard` → test rows; `qa-steps-for-eng` for a PR), run by the main session, which persists the returned rows as the QA snapshot; `framework-qa-reviewer` reviews the framework, not a product, and has no write tools. Before naming any doc 38 skill in a brief, check its `disable-model-invocation` and preconditions (draft PR vs ready PR); a skill that cannot run is a human-only row in the memo, not a dispatched lens.

04. **Estimate input size and choose models** (`selection.by_input_size` in the registry): `wc -w` the input artifact(s) × 1.35 ≈ tokens; if that exceeds 60% of a role's primary window, use the role's `long_window` model (Gemini when wired, else Astra) or chunk per file with a merge step. Record the estimate and the choice in each lens snapshot's frontmatter. **Assign families** from `models/model-registry.yml`: author family from the input snapshot's `produced_by`; adversary must differ; synthesizer differs from the majority. If shunt is needed and not running, say what to start (`brew services start shunt`, `ANTHROPIC_BASE_URL`). Where independence is impossible, tag the lens `independence: same-family` and carry it into the memo.
    3a. **Design changes: Astra xhigh, always** (doc 17 §6.3). For erd and plan kinds, and for a pr that changes the design (decide records a choice on an already-reviewed `design_sha` and does not trigger a new review), one cross-family review of the design artifact by `gpt-6-astra` at `xhigh` is required regardless of size: `council-adversary` or `infra-lens` through shunt, or `codex exec -m gpt-6-astra -c model_reasoning_effort="xhigh" -c sandbox_mode="read-only" --skip-git-repo-check - < brief` in the background (doc 44 §3). Confirm the served model with `scripts/served-models.sh` and write it into the lens snapshot and the ERD's §8 table. When the artifact's author family is OpenAI, also run the brief on `anthropic/fable-5-1` as the independent reader. If OpenAI is unreachable, run it on `anthropic/fable-5-1`, tag `independence: same-family`, keep the design `in review`, and put "accept on a same-family review?" as a human gate needing a named waiver in the decision record. At most two passes per design (doc 46 §4): one on the full design, one on the delta that fixed its blockers; a fallback run takes the slot of the pass it stands in for.
    3a-bis. **Medium and high default** (doc 43 §6). Read the size from the intake snapshot (reclassify against the diff for pr). For medium and high, the council includes **one consolidated cross-family review** of the artifact (the design artifact for prd/design/erd/plan, the diff for pr), not one per lens. It is the adversary the round already runs, not an extra reviewer: for the design artifact, Astra (gpt-6-astra, extra-high) through Codex or `council-adversary` through shunt; for the pr kind, the existing `/codex:adversarial-review`. Its findings go into the memo as advisory input to the human gate; it never approves. If no second family is reachable, the memo and the gate record say so. Record its tokens, minutes and prompt characters in the ledger (`--tokens --minutes --prompt-chars`) and in the memo.
    3a-ter. **Review loop budget, every pr, design and erd kind** (doc 46 §4, §5). The cross-family lenses of one round (the adversary, plus `infra-lens` on backend code) run in parallel and together are one pass. Pass 1 reviews the full change; pass 2 reviews the delta only (the fixes, with pass 1's findings as the question). If pass 2 still has blockers, stop: the memo gives the human options (accept with a named follow-up, rework, or one more pass) with their minutes and tokens; no pass 3 unless a human explicitly asks, recorded in the snapshot. Each brief is the diff (or delta), the specific question and file pointers by path and line; no pasted file bodies; 15,000 characters or fewer; a longer brief says why in its first line and is a named breach in the loop report. Excerpt-only routes (Glean, `--tools ''`) are the exception and are tagged `excerpt-only`. The memo snapshot carries the loop report line (doc 46 §6).
    3b. **Independence, effort and budget.** Resolve the host (`hosts:` in the registry): in Claude Code the adversary family is OpenAI via shunt, in Codex it is Anthropic via `claude -p`. Pick the effort the role names: Astra xhigh for erd/plan/prd adversary and synthesis, Sol medium for the pr adversary, Sol low for research digests; when shunt's provider default is not the effort you need, run that lens as `codex exec -c model_reasoning_effort=<level>`. The author family is the family that produced the *artifact* (its own snapshot's `produced_by`, or the commit authors and their recorded tooling), not whoever wrote the council input snapshot; mixed or unknown authorship is tagged `independence: unknown`, never treated as independent. The adversary must differ from the author family; the synthesizer differs from the majority. Resolve a *reachable* model: probe shunt (`curl -s http://127.0.0.1:3001/`) and `host_routes` in `~/.claude/harness-profile.yml`; if the primary is unreachable follow the registry fallback order for the kind. prd/design: Codex plugin, then the Glean family (call `glean_default.chat` with the lens brief plus the artifact text, chunking with the `context` array so each message, brief included, stays within doc 46's 15,000-character target; save the reply yourself as the lens snapshot with `produced_by: glean/glean-assistant` and `independence: unknown` until `glean.assistant_model` is confirmed), then the same-family Anthropic fallback, tagged. erd/plan/pr: Codex plugin, then the same-family Anthropic fallback, tagged; Glean is not the adversary for code kinds (it sees only your excerpts), but you may append its reply to the memo as a section titled "Second reading (Glean, not counted)". Say which route ran in the memo. The only non-Anthropic route is OpenAI through shunt; Gemini is Glean-only and DeepSeek has no lane (doc 37 §3), so a lens that needs a 1M window chunks its input instead. After each lens returns, record the model actually served (agent result or shunt log) in the lens snapshot's `produced_by`; a model named only in the brief is a request, not evidence. Budget: per lens, input words × 1.35 + 30k for instructions and tool schemas, × 1.5 headroom for tool reads; sum over lenses plus one retry; if the sum exceeds the profile's `council_budget` (default 600k) stop and ask; record actual `tokens` per lens in the ledger.

05. **Dispatch all lenses in one message** with the Agent tool, each through the agent type its registry role names (doc 44 §1: never `general-purpose` for a lens, because it inherits the session's base model), under the sub-agent guards of `${CLAUDE_PLUGIN_ROOT}/framework/51-sub-agents.md` (doc 51 is authoritative; this dispatch uses `council_budget` as its token budget with the one estimate rule of step 3b above). The adversary is `subagent_type: council-adversary` and the synthesizer `council-synthesizer` (both `model: gpt-6-astra` through shunt, WITH repo tools); fall back to the detached CLI recipe when the agent type is not in this session's roster (agent files load at session start) or when `curl -s http://127.0.0.1:3001/` fails. The CLI fallback keeps repo access with `--allowedTools "Read,Grep,Glob,Bash(git *),Bash(rg *)"`; use `--tools ''` only if that fails, and tag that snapshot `excerpt-only`. The research lens must write rows to its snapshot after every question and cap each tool result (≤ ~4k tokens: `sed -n` ranges, WebFetch prompts that ask for a digest); a lens that dies on context is re-run once on the role's `long_window` model, then escalated. Each brief: the input snapshot path, the lens checklist from doc 34, the registry role, the model, and the instruction to write `runs/<run-id>/council.<slug>.<lens>.md` with pass/fail rows, options with a recommendation, and sources for every fact. No lens sees another's output.

06. **Reconcile against disk.** When lenses return, open each snapshot; a report that does not match its snapshot is discarded and the lens re-run once.

07. **Synthesize.** The memo publishes a Notion page (doc 33, `templates/notion-page.md`) beside the `.md`; the Notion page is what the human reads and its URL goes in the report.
    6 (cont). Dispatch the synthesizer (`pr-tech-lead-synthesizer` pattern, family per registry) with only the lens snapshot paths. It writes `runs/<run-id>/council.<slug>.memo.md`: agreements, disagreements with both sides quoted, options with one recommendation each, human gates to open, and every `same-family` tag.

08. **Notion page for the memo** (doc 33; `templates/notion-page.md`, plain voice, the options table verbatim, the go-ahead questions verbatim); write its URL as `notion:` in the memo frontmatter and in `index.md`. Lens files get no page. The round is not reported without the memo URL.
    7b. **Ledger + index + share.** Prepare one ledger event per lens and one for the memo; append them with `ledger/append.py` in local storage. In notion storage, append each lens event with `storage.py ledger-entry`; the `post-update.py` call below appends the memo event, so do not append it first. Update `runs/<run-id>/index.md`; then `bash "${CLAUDE_PLUGIN_ROOT}/scripts/record-sync.sh" push <initiative> "<initiative>: council <slug>"`. Run `post-update.py --stage council.<slug> --summary <memo-summary> --links <memo-and-page-links> --issue <issue-if-given> --initiative <initiative> --run <run-id> --event <memo-event-id> --agent <memo-agent> --outcome <memo-outcome> --profile <profile>` and execute every call in its JSON plan. Six lens snapshots and a memo that live only on one laptop are not a council record; exit 2 is reported and the round is not done.

09. **Report** the memo path and its options table. First save the draft report and run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/verify-claims.py <report.md>`; add evidence beside every unsupported completion claim. On a surface without Bash, apply the same evidence rule manually and say the script could not run. Do not restate lens findings. Ask the human to pick; do not proceed on a recommendation alone when the memo names a gate.

10. **Record the decision** when the human picks: `/harness-council <initiative> decide <memo-slug> <option> "<who>" "<rationale>"` writes `runs/<run-id>/council.<slug>.decision.md` (its own Notion page, URL in `notion:`; option chosen, who, rationale, the memo's sha and every input sha it rests on, remaining conditions, gate id and its new status) and one ledger event with `--human`, `--human-rationale`, `--gate-override`, then `bash "${CLAUDE_PLUGIN_ROOT}/scripts/record-sync.sh" push <initiative> "<initiative>: decision <slug>"`. Run `post-update.py` for the decision stage with `--initiative`, `--run`, `--event`, `--agent` and `--outcome` copied from that event, and execute its plan. A later change to any recorded input reopens the decision for that scope. A recommendation never fills this record; only a named human does.

## Hard rules

- Gate rows are `checked`, `failed`, `unverified` or `not applicable`; a row nobody could check is `unverified`. Models agreeing is not approval.
- Compliance verdicts are human. A lens may quote the register and mark a check `needs human`; it never rules.
- At most two rounds; the third is an escalation. At most two cross-family passes per artifact, the second on the delta only (doc 46 §4).
- Never run a whole session on a non-Anthropic model; lenses are discrete calls whose input and output are files.
- Never trust a lens report over its snapshot on disk.
- A missing, timed-out or malformed required lens makes the round `incomplete`; the memo says so and no option is marked recommended until it is rerun or a human waives it in the decision record.
- A rerun writes `council.<slug>.r2.<lens>.md`; the first round is never overwritten.
