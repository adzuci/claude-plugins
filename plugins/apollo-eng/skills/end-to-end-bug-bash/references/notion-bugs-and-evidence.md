# Test Case + Bugs DB Evidence Attachment (Phase 4)

## Upload primitives (native first)

For every local evidence upload:

1. Prefer callable native Notion `create_file_upload` and `create_attachment` tools. Inspect their
   live tool schemas and use the returned upload/file handle as directed; do not guess parameters.
1. If the Notion profile reports those capabilities but the tools are not exposed or callable in the
   current runtime, treat native upload as unavailable. Use the authenticated-browser fallback below.
1. Never upload credentials, authentication state, or an unscrubbed trace/HAR. Never substitute a
   local filesystem path in Notion page text for the required attachment.
1. Re-fetch the page after a native upload, or snapshot it after a browser upload, and verify the
   expected filenames appear before recording the evidence state as `Uploaded`.

### Authenticated-browser fallback

Use a separate persistent `playwright-cli` session authenticated to Notion (`-s=notion`), not the
session driving the app under test. Load saved state when available. Otherwise, perform the one-time
headed login disclosed during preflight and save state for the rest of the run. Navigate to the
target row, locate its existing file property's upload control, click it, and run
`playwright-cli upload <local-path>` for each file.

## Executed Test Case evidence (all outcomes)

Every executed Notion Test Case gets evidence, including Pass cases:

- `report.md`
- the screenshots applicable to that case (failure screenshots are mandatory)
- the run video
- a trace/HAR only when it was confirmed scrubbed

Fresh-fetch the Test Case data-source schema and select an existing `file`/`files` property. Prefer
**`Video Recording`** when it exists and is a file property. If there is only one file property, use
it. If multiple file properties remain genuinely ambiguous, ask once which existing property to use.
Never create or rename a property to work around the ambiguity.

After uploading, verify the attached filenames. Write `Evidence upload: Uploaded` plus those names in
the run summary and local report. If neither upload method works, keep the functional
Pass/Fail/Partially pass result unchanged, write `Evidence upload: Pending` plus the exact blocker in
both places, and do not call evidence delivery or the overall run complete.

## Bugs DB rows (failed outcomes)

Bugs DB: `collection://87d4a43c-f949-4736-be96-87d37c57d2f5` (title `Title`). Its "Bugs found"
section on every Test Plan page is a filtered view into this same DB.

## Creating the row

Use `notion-create-pages`:

```javascript
{
  "parent": { "type": "data_source_id", "data_source_id": "87d4a43c-f949-4736-be96-87d37c57d2f5" },
  "pages": [{
    "properties": {
      "Title": "[One-line description of the failure, not the fix]",
      "Feature": ["[this feature's Test Plan page URL]"],
      "Test Case": ["[failing Test Case page URL, if identifiable]"],
      "Priority": "[P0|P1|P2|P3|P4]",
      "Status": "Not started",
      "isBlocker": "[No|Yes|In progress]",
      "Tags": ["Enhancement"]
    },
    "content": "## This is Generated by AI\n### Description\n[what's wrong]\n### Environment\n[URL], account [login/email — never password]\n### Preconditions\n[exact state needed to reproduce — data, flags, account type]\n### Steps to Reproduce\n1. [step]\n### Expected Result\n- [expected]\n### Actual Result\n- [actual, quote real error text]\n### Impact\n[who hits this and how badly, one or two sentences]\n### Evidence\nSee the \"Files & media\" property on this page for screenshot(s)/video/scrubbed trace (if any)."
  }]
}
```

Setting `Feature` to the Test Plan page URL is what surfaces the bug under that page's "Bugs found"
section — a relation value, not manually placed content.

- `Jira` — leave blank at creation; only set via the link-back step (`jira-filing-rules.md`), once a
  ticket actually exists.
- `isBlocker` — `Yes` only if the bug actually blocked further execution; don't default to `Yes`.
- `Tags` — `Enhancement` for suggestions/observations rather than genuine defects.
- `Severity` — optional, rarely populated in real usage; don't force a value.

**`content` is the full write-up, matching `bug-report-template.md`'s per-bug section field-for-field**
(Description/Environment/Preconditions/Repro/Expected/Actual/Impact) — the Notion row is the primary
record, not a summary pointing at the local file. Keep `## This is Generated by AI` first, matching
the same convention on Test Case DB rows.

## Attaching bug-specific evidence

The Bugs DB has two unused `file`-type properties for this: **`Files & media`** and **`Screenshot`**.
Use one; never invent a new property or fall back to a text-only path reference.

Use the native-first flow and browser fallback above.

1. Target `Files & media` (or `Screenshot`). Prefer `Files & media` for trace/HAR — it isn't a
   screenshot.
1. Repeat per evidence file for this bug: screenshot(s), the run video if this is the bug that
   produced it, and the scrubbed trace/HAR if `SKILL.md` Phase 3's credential-safety rule confirmed
   it's genuinely scrubbed (never upload an unscrubbed one).
1. Once all of this bug's evidence is uploaded, snapshot once more to confirm everything shows
   attached — one confirm per bug, not one per file — before moving to the next bug.

Evidence lives in Notion now, not just a path pointing away from it. The local
`bug-report-<feature-slug>.md` stays a secondary local backup.
