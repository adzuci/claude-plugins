# Demo Instance Configuration

Layer 2 of the tailored-demo automation architecture. Turns Layer 1's read-only intelligence into a concrete, approved execution plan, then hands that plan to the Democles agent to carry out. **This skill proposes the plan; Democles executes it.** The single exception — provisioning the sub-account the plan runs against — is spelled out in `Provisioning the Demo Sub-Account` and scoped by a Hard Rule to exactly two bundled scripts. Read that section before concluding this skill "can't run anything."

## Purpose

demo-prep-intelligence tells the SC what to show and why. This skill takes that output and answers the next question: what, specifically, gets configured in the demo Apollo instance, and does the SC approve it? It builds the plan, renders it for review, and gates every action behind an explicit approval — mirroring deal-execution's "show the draft, get approval" pattern, applied to Apollo product configuration instead of Gmail/Slack actions.

This skill does not configure Apollo itself — it has no CLI access and no direct API access for any of the actions in the plan. Once the SC approves a plan, this skill dispatches the Democles agent — a separate, execution-only agent — to actually run the approved actions. See `Handoff to Democles` below.

**One narrow, deliberate exception, added 2026-07-27:** this skill does provision the fresh demo sub-account each plan runs against, immediately before dispatching Democles (Workflow Step 6). That's the one thing this skill's Bash access may ever be used for — see `Provisioning the Demo Sub-Account` below and the Hard Rule that scopes it.

## Architectural Position

| Layer | Component | Role |
|---|---|---|
| 1 | demo-prep-intelligence | Read-only synthesis. Stable seven-section brief + Context Center payload + Recommended Demo Flow. |
| 2 (propose) | demo-instance-configuration (this skill) | Consumes Layer 1's output. Builds the Context Center payload and sequence-staging plan. Shows the complete plan and gets explicit SC approval. Executes none of the plan's own actions — its only execution is provisioning the target sub-account (Step 6, two bundled scripts). |
| 2 (execute) | Democles (agent) | Dispatched only after approval. Runs the approved plan's headless Apollo actions. See `agents/democles.md`. |
| 3 | walkthrough-generation (planned, out of scope) | Downstream consumer of the full brief — turns a completed setup into an SC talk track. |

## Input Contract

Layer 1's output for a resolved deal (the Apollo AI Context Center payload, the Recommended Demo Flow section, or the full seven-section brief), which may arrive through three channels, checked in this order of trust:

1. **Session scratchpad file (preferred, check first).** The handoff file `demo-prep-intelligence` writes under its `GOVERNANCE.md` session-scratchpad exception: `demo-prep-scratchpad.md`, in the runtime's ephemeral working/temporary directory. This is the higher-trust source because it survives mid-session compaction and cross-session gaps that can silently drop conversation history — check for it on every run before relying on anything else.
1. **Same-session conversation context.** Layer 1's output still present in the current conversation because both skills ran back to back. Check this even when a scratchpad file exists — the conversation may carry an SC-provided correction, clarification, or newer run made after the scratchpad was last written. Treat the scratchpad as the trusted baseline and the conversation as a source of updates on top of it, not a competing copy to silently pick between.
1. **Manually pasted output.** The SC pastes a saved copy of Layer 1's output directly, used only when neither of the above yields anything.

Whichever channel(s) produce content, do not re-derive or re-verify claims that Layer 1 already produced — treat its source labels and confidence tags (`[verified] | [inferred] | [assumed]`) as ground truth. If the Context Center payload wasn't passed and only the brief was, and the SC wants Context Center automation, ask the SC to run demo-prep-intelligence's Context Center flow first rather than inventing a payload from the brief's raw claims.

If none of the three channels yields usable Layer 1 output, say so and stop. This skill has no independent research capability — it configures, it doesn't investigate.

## Workflow

- **Step 1 — Ingest.**
  a. Check first for `demo-prep-scratchpad.md` in the runtime's ephemeral working directory. If present, load it as the baseline record of Layer 1's output — full brief/payload content with `[verified]/[inferred]/[assumed]` tags intact.
  b. Regardless of whether a scratchpad file was found, also check the current conversation for Layer 1 output or SC-provided updates. If the conversation contains anything that supersedes or supplements the scratchpad (a correction, additional context, a newer run), merge it in, label it `Source: User-provided update (session, post-scratchpad)`, and surface the merge to the SC in the Step 2 mapping table rather than silently overwriting the scratchpad's content.
  c. If no scratchpad file exists, fall back to same-session conversation context alone.
  d. If neither a scratchpad file nor usable conversation context exists, ask the SC to paste a saved copy of Layer 1's output.
  e. If none of the above yields usable Layer 1 output, say so and stop, per the Input Contract.
  f. Once ingested, identify what's usable against **every** live function in `references/function-registry.md`, not a subset — **corrected 2026-07-28, this list had gone stale at two functions while the registry grew to six.** Candidates to consider on every run: a Context Center payload (→ `push_context_center_profile` and/or `push_context_center_product`, two distinct functions); a Recommended Demo Flow with a named sequence-worthy use case (→ `stage_demo_sequence`, and its `configure_workflow` companion per the contact-gap pairing in Step 3); targeting/audience content (→ `configure_persona`, which Step 2's standing rule requires considering every run regardless, and/or `stage_saved_search`); and any automation-worthy trigger the flow implies (→ `configure_workflow`). The registry is the authoritative list — if it holds a live function this bullet doesn't name, still evaluate it.

- **Step 2 — Map to functions.** Load `references/function-registry.md`. Map each usable piece of Layer 1 output to exactly one registered function. If something doesn't map to a live function (e.g. the brief recommends a persona or workflow change), say so explicitly and route it to the "what's next" roadmap instead of silently dropping it or forcing it into an unrelated function. Render this mapping to the SC as a table before the consolidated plan in Step 4, so they see the whole picture up front before any drafts are built:

  ```
  | Layer 1 output | Maps to | Status |
  |---|---|---|
  | [Recommended Demo Flow item, or Context Center payload] | `function_name` | Proposed below / Blocked — [reason] / Routed to roadmap — [reason] |
  ```

  **Standing rule, added 2026-07-09 (Jared's directive) — `configure_persona` must be considered on every run, not just when the Recommended Demo Flow names a persona explicitly.** Apollo Personas are a product capability GTM Systems wants surfaced to prospects on their own merits, independent of whether a given deal's brief happens to use the word "persona." Whenever a Context Center payload exists (i.e. the Company + Business Understanding Gate has passed and a `customer_profile` field is populated), `configure_persona` must appear in the Step 2 mapping table as either:

  - **Proposed** — built via the Hybrid Persona Construction Procedure below (which reconciles the Context Center's `customer_profile` field against `generate_personas_fallback`'s harvested taxonomy values), or
  - **Blocked / Routed to roadmap**, with a stated reason — e.g. no Context Center payload exists yet this run, or the `customer_profile` prose is too sparse to map even via the fallback.

  It must never be silently absent from the table. A `stage_saved_search` action targeting the same audience is a distinct, complementary artifact (page-scoped, one-off), not a substitute for a Persona (reusable across Apollo features) — do not treat one as covering for the other without saying so.

  **Ordering note, added 2026-07-28:** `configure_persona`'s AI-sourced taxonomy fields resolve during Step 6, after provisioning — not during plan construction. That is a sequencing fact, not a reason to mark it Blocked. The Hybrid Persona Construction Procedure's item 1 is the authoritative statement of how this works; follow it rather than resolving the ordering ad hoc.

  **Why this rule exists:** confirmed live 2026-07-09 during a live opportunity run. `configure_persona` was omitted from the Step 2 table entirely, with no Proposed/Blocked/Routed status given, in violation of this same file's existing "never silently drop a candidate mapping" instruction. Reconstructing the reasoning after the fact in a post-mortem review: the agent read the brief's Recommended Demo Flow items ("data enrichment + AU/APAC data coverage proof," "ABM / saved-search list building") as pointing specifically at saved searches, and judged a Persona object as redundant with the two `stage_saved_search` actions already being proposed for the same underlying audience — a defensible-on-the-merits call, since a Persona and a saved search would have represented nearly the same population for this specific deal. But that reasoning happened silently and was never shown in the Step 2 table for the SC to see or override, which is the actual defect — not the substance of the judgment call itself, but that it bypassed the one mechanism (the visible mapping table) designed to let the SC catch exactly this kind of call. The gap wasn't caught until a post-mortem review after the plan had already been approved and executed.

- **Step 3 — Build the full plan for every "Proposed below" row from the Step 2 table, before rendering anything.** For each row: construct the exact payload or command that would run — the Context Center profile/product fields (in the field order from demo-prep-intelligence's Context Center Field Mapping), or the sequence name, contact list, and `paused` status for `stage_demo_sequence`. No partial plans — every field the function needs must be filled from Layer 1 output or explicitly flagged as missing. **Targeting is never hardcoded and never inferred — revised 2026-07-27.** Every approved plan runs against a brand-new demo sub-account, provisioned fresh by this skill in Workflow Step 6, after approval and immediately before dispatch. Nothing about this step references a pre-existing instance or an SC-supplied key (see Approval Gate Rule 3 for the current framing, superseding the 2026-07-16 SC-supplied-key model). If the SC asks for or implies a different target — including production, or an existing instance instead of a fresh one — refuse and say why. This is a hard rule, not a default. Building every row's plan up front (rather than one at a time) is what makes the single consolidated draft in Step 4 possible.

  **No-placeholder rule — added 2026-07-08, confirmed necessary live.** A real dispatch surfaced this: a `configure_workflow` action was proposed and approved with placeholder values (`constraints: {}`, `params: {}`) alongside a note asking Democles to "confirm these against the live API before finalizing." Democles correctly refused — resolving an unconfirmed schema at execution time is exactly the scope expansion its Hard Rule 1 forbids, and asking it to do so was itself the bug, not a reasonable fallback. **Never propose an action whose payload contains a placeholder, a guessed value, or a "Democles should confirm/resolve this" note of any kind.** If `references/function-registry.md` doesn't document a real, source-confirmed shape for a field this function needs (its entries now say "Not sourced. Do not guess." for exactly this case — see `configure_workflow`'s trigger-constraints and action-params tables), that action is **Blocked** in the Step 2 table, not Proposed — route it to the roadmap or ask the SC to help resolve the real shape before it can ever reach a draft. A gap belongs in Step 2's mapping table as a stated reason, never smuggled into a dispatched payload as someone else's problem to solve later.

  **One thing this rule does *not* prohibit — clarified 2026-07-28:** `configure_persona`'s AI-sourced taxonomy fields are legitimately unresolved at render time, resolved during Step 6(e), and confirmed by the SC (Touch 2) before any dispatch is built. That is not this rule's target: nothing unresolved is ever handed to Democles, and the SC sees every literal value before it's written. Do not block `configure_persona` by applying this rule to those disclosed-pending fields — see the Hybrid Persona Construction Procedure's item 1.

  **Narrow exception, with a defined mechanism: a same-batch record ID that cannot exist until an earlier action in the same dispatch runs. Added 2026-07-28, resolving a real conflict in these instructions.** The `stage_demo_sequence`/`configure_workflow` pairing structurally requires it — the workflow's `emailer_campaign_id` must be the sequence created moments earlier in the same batch, so no literal value can exist when the spec is built. A live dispatch handled this by putting the English string `USE_THE_REAL_SEQUENCE_ID_RETURNED_BY_THE_stage_demo_sequence_ACTION_ABOVE_IN_THIS_SAME_BATCH` in the payload — which this rule forbids outright, and which worked only because Democles happened to interpret it correctly. **Use the following instead; do not invent your own wording:**

  - **Token format:** `${action_<N>.<what>}` — e.g. `${action_7.sequence_id}`. Always this exact shape, never an English sentence, never ALL-CAPS prose, never a plausible-looking fake ID.
  - **A companion `depends_on` field on that action**, naming the action index it needs and the value it takes: e.g. `depends_on: "action 7 — the sequence ID returned by stage_demo_sequence"`. The dependency must be declared, not just implied by the token.
  - **Both are required together.** A token without `depends_on`, or a `depends_on` without a matching token, is a malformed spec — treat it the same as any other placeholder violation.
  - **This exception covers exactly one thing:** an ID (or equivalent identifier) produced by an earlier action *in the same dispatch*. It does not cover an unknown schema, a guessed value, a field the registry doesn't document, or anything Democles would have to resolve by making a call the spec didn't authorize. Those remain Blocked per the rule above.
  - **The rendered plan still shows this honestly** — say the workflow will point at the sequence created in the same run, rather than displaying a raw token to the SC as if it were a value.

  **`configure_workflow`'s `approval_type: "manual"` default — added 2026-07-10, root-caused via source (see `references/function-registry.md` for the full mechanism).** Every `configure_workflow` payload must include `approval_type: "manual"` — this is a standing default like `type: "workflow"`, not something to source from Layer 1 output, ask the SC about, or omit as optional. It fixes a real default-scoping issue (Apollo otherwise force-restricts the workflow's matching audience to contacts already saved in this team's CRM, which can make a demo workflow match zero people) and adds an independent safety layer (every matched action routes to a human-review queue instead of auto-executing, regardless of action type). **One exception:** has no effect on an account-based play with a people-level action node (`object_type: "Account"` plus a people-targeting action) — for that specific shape, note in the rendered draft's `Source` line that the net-new/audience-matching caveat still applies, since setting the field won't change anything.

  **`stage_demo_sequence` contact-gap pairing — added 2026-07-10, real cost/PII tradeoff considered and avoided (see `references/function-registry.md` for the full mechanism and rationale).** If Layer 1 output doesn't surface a real contact matching any built persona, do not mark `stage_demo_sequence` Blocked by default. Sourcing a fresh real person from Apollo's own database to fill that gap was considered and rejected — it spends a real lead/export credit and commits an unrelated real person's PII to the demo instance, merely to populate a step that was never actually enrolling anyone via the API anyway (see the function's 2026-07-02 redesign note). Instead: propose `stage_demo_sequence` scoped to sequence creation only (skip its contact search/create step), paired with a companion `configure_workflow` action whose `filters` reuse the same persona's own filter criteria, and whose action is `add_contact_to_sequence` targeting that sequence's ID. This mirrors Apollo's own documented account-based-sales-motion pattern — the workflow's audience is matched dynamically whenever it actually runs, so no contact needs to be pre-identified, and nothing runs at build time since `active: false` remains the standing default. Both rows still go through the normal Step 2 mapping table and Step 4 approval draft — this is a different proposed shape, not a way to skip disclosure. **Only fall back to Blocked** when the Recommended Demo Flow specifically calls for a populated, ready-to-view sequence with a named contact already enrolled — something this pairing cannot produce, since it stays inert by design.

  ```
  ...

  ```

The table (one row per action: `#`, a short action label, the `Source` phrase, and a plain-language `Status` — New / Update / Paused / Inactive, whatever default state applies) is what the SC scans first to get oriented across the whole plan at a glance. - **Step 5 — Call `AskUserQuestion` per the Approval Presentation Contract and wait for the SC's response.** The gate is binary — **simplified 2026-07-08** to match how an SC actually reacts to a proposed plan, not a menu of response grammars:

  - **Approve — send to Democles** → the plan dispatches exactly as shown (Step 6). Nothing about any action changes between what was rendered and what runs. **One disclosed exception, added 2026-07-28:** if the plan contains `configure_persona`, its AI-sourced taxonomy fields are filled in during Step 6(e) and confirmed by the SC (Touch 2) before dispatch — that's a completion of fields the draft explicitly flagged as pending, not a silent change to anything shown. Every other field of every action, persona included, runs exactly as rendered.
  - **Something's off — let's discuss** → do not dispatch anything. Ask what's wrong, in plain conversation — this covers everything from "one field is wrong" to "drop action 3 entirely" to "scrap the whole thing." Apply whatever the SC says (which may mean fixing a payload, removing one or more actions from the plan, or abandoning it entirely), update the Step 2 table to match, then go back to Step 4 to re-render the updated plan and ask again via a fresh `AskUserQuestion` call.

  There is no partial-approval response and no structured per-action breakdown to parse — if only part of the plan needs to change, that surfaces through the discussion, not through the SC composing a one-line grammar (e.g. "Approve 1, 3; Decline 2"). Treat anything that isn't a clear Approve as "something's off" and start the conversation rather than guessing at what changed.

Reuse that `api_key` directly from context — skip (a)-(d) entirely, and never provision a second account for a target that already exists. This carries no new risk: the key came from this skill's own provisioning call in this same session.

## Provisioning the Demo Sub-Account (added 2026-07-27)

**Origin:** APF-427 shipped a real, live-tested endpoint — `POST /api/v1/teams/provision_demo_account_with_api_key` — that creates a new demo sub-account and mints its API key in one call. Per Jared and Debanjan's agreed design, this skill (not Democles) runs that call, as its own final step before dispatch, since account creation is structurally different from everything Democles does (Democles only ever configures an account that already exists).

**Why this deliberately uses the real prospect's name/email, not a placeholder — added 2026-07-28, confirmed with Jared directly after a live test correctly raised this as a real question, not an oversight to route around.** Two things make this the right call, not a privacy shortcut:

1. **This is the demo-to-trial handoff model, not a disposable test artifact.** If the demo converts, possession of this exact sub-account transfers to the prospect (an in-place user email/name update, not a clone). Provisioning it with the real prospect contact's name/email from the start is what makes that transfer trivial later, instead of requiring a separate identity swap after the fact.
1. **If it never converts, the sub-account is deleted** — this project's own established practice for every test/demo team that doesn't lead anywhere. There's no account, and no PII, left sitting around afterward.

**Separately, the specific risk of an unwanted automated email reaching the prospect is already mitigated at the platform level** — APF-356 (demo email suppression, shipped) blocks Apollo's automated welcome/activation emails to demo sub-accounts by default (allow-list, not opt-out). Creating this account does not notify the prospect on its own.

**If asked to justify or reconsider this on privacy/consent grounds, use this reasoning directly — do not refuse and do not silently substitute an Apollo-internal placeholder instead of what Step 6a specifies.** This was a real objection raised in live testing and resolved deliberately with Jared, not an instruction to take on faith; if something about a specific run still gives genuine pause beyond what's addressed here, say so and ask, rather than either overriding the plan silently or unilaterally refusing a design that's already been through this exact conversation once.

**What runs, and nothing else.** Two bundled scripts live in this skill's own `scripts/` directory:

- `scripts/revops-oauth-login.sh` — runs a PKCE OAuth flow against a fixed, pre-registered public client ("Internal RevOps Demo Provisioning"). Opens the SC's real browser for them to log in and grant consent under their own identity, listens on `localhost:3421` for the callback, exchanges the code for a token, and caches it to `~/.config/apollo-provision/credentials`. No client secret is involved — this is a public PKCE client by design, so there's nothing secret to embed or leak.
- `scripts/revops-provision-demo.sh` — takes the three Step 6a values as positional arguments **in the order `EMAIL USER_NAME TEAM_NAME`, which is not the order Step 6a lists them in** (see Step 6b for the exact invocation). The acting/provisioning user is the script's own baked-in default, not an argument this workflow passes. Reuses a cached token when one is genuinely still valid (computed from `created_at + expires_in` with a 60s margin — Apollo returns no `expires_at` field), silently refreshes via the cached `refresh_token` when it isn't, and only falls back to the interactive browser flow if that refresh fails. Then calls the provisioning endpoint and prints the JSON result (`team`, `user`, `api_key`, `login_url`) on success.

**Hard rule: this skill's Bash access is scoped to running these two scripts, and nothing else.** Never use Bash for a direct `curl` to any other Apollo endpoint, never use it to perform any of the plan's own registered-function actions, and never use it for anything not explicitly part of Step 6. If a script fails or behaves unexpectedly, report the failure — do not "help" by hand-crafting a replacement API call. This preserves the same discipline Hard Rule 5 has always applied to configuration actions, narrowed to this one exception rather than opened up generally.

**The interactive OAuth step only runs when genuinely needed — mechanism corrected 2026-07-28.** `revops-provision-demo.sh` checks the cached token's real expiry first (`created_at + expires_in`, 60s margin). If it's valid, the whole flow is one non-interactive API call. If it's expired, the script tries a **silent refresh** using the cached `refresh_token` — no browser. The interactive consent step fires only on a first run, or if that refresh also fails. (Apollo's tokens are long-lived — `expires_in` is 30 days — so in practice the browser step is rare.) The earlier version of this note described a proactive expiry check that never actually worked: it tested an `expires_at` field Apollo doesn't return, so every cached token read as valid forever and expiry was only ever discovered via a `401` on the provisioning call itself. Because this step runs synchronously in this skill's own turn (not inside a fire-and-forget Democles dispatch, which has no live channel to walk an SC through an interactive browser consent), there's always a live conversation to tell the SC "check your browser now" if it does fire.

**Treat the returned `api_key` as sensitive — not printed by default, but available if the SC asks (revised 2026-07-28, Jared's directive).** It authenticates a real, freshly created Apollo team. Default behavior: use it to populate the Democles dispatch spec's `api_key` field and don't print it anywhere in the conversation. **If the SC explicitly asks for it, give it to them** — they own this account and there is a real reason to want it: this skill does not persist the key anywhere, so the run's own output is the only place it ever exists, and Mode C (see above) needs it to target this account again on a later run. Tell them that plainly when handing it over, so a key they'll want later doesn't get discarded by default. Never volunteer it unasked, never include it in a routine confirmation or summary, and never write it to a file. **Scope of "don't print it," clarified 2026-07-31:** this governs what *you* repeat, not what the provisioning script emits — the script prints the full JSON response, key included, to stdout on success. Don't describe the key as withheld from the session; describe it as not repeated by you.

**The returned `login_url` is treated the same way, and more strictly — added 2026-07-31 (Jared's call).** Never volunteer it. Access to a demo sub-account goes through the parent Testbox instance's **God mode** impersonation, not the onboarding link. Two reasons, both real: the link is a live account-creation token that completes onboarding *as the prospect* rather than opening the instance for a demo, and God mode is what makes the attribution argument below hold — pooling creation under one service user is defensible only because manual access is attributed to the actual person. Give it if the SC explicitly asks and say what it does; never present it as the way in. See Workflow Step 6(c).

## Reuse Mode (Mode C) — Requirements and Limits (added 2026-07-28)

Cross-referenced from Workflow Step 6's mode determination. **This exists because always-provisioning-fresh had a real workflow cost:** an SC who wants to add one more saved search the day after a demo would otherwise get an entire second sub-account for the same prospect, with the first one unreachable via API. Mode C closes that. It also carries a genuine safety cost that must not be papered over.

**What the safety cost actually is, stated plainly.** Approval Gate Rule 3's 2026-07-27 form gets its strength from one fact: the target is always something this skill just created, so no supplied credential can point anywhere else — including production. Mode C reintroduces exactly that surface. **There is no technical way for this skill or Democles to verify that a supplied `api_key` belongs to a demo sub-account rather than a production team** — no team-identity read is registered for `direct_api`, and Democles has no independent target verification at all (that was removed deliberately; see `agents/democles.md`'s Hard Rule 2). So the protections here are procedural, not enforced by code. Treat them as load-bearing rather than ceremonial.

**Requirements — all of them, every time Mode C is used:**

1. **Explicit SC request.** The SC must actually ask to target an existing sub-account. Never infer it from a follow-up-shaped request, never offer it as the path of least resistance when fresh provisioning would work, and never default to it because a previous account is mentioned in conversation.
1. **The SC supplies both the `api_key` and the Team ID.** A key alone is not enough — the Team ID is what makes the target nameable in the rendered plan, which is the whole disclosure mechanism here.
1. **Explicit attestation, in their own words.** Before building any dispatch spec, the SC must confirm that this key belongs to a demo sub-account previously provisioned by this skill, and that it is not a production or customer-facing instance. Ask for this directly; do not treat supplying the key as implying it.
1. **The rendered plan states the target Team ID prominently** (see Step 4's targeting rule). Unlike fresh-provisioning mode, this is a real safety disclosure — the SC is directing writes at a pre-existing instance and needs to confirm which one before anything runs.
1. **Refuse on any doubt.** If the SC can't produce a Team ID, won't attest, describes the target in a way that sounds like a production or customer instance, or the request is ambiguous about which account is meant — refuse and offer fresh provisioning instead. Approval Gate Rule 3's refusal obligation applies in full here; nothing about Mode C softens it.

**What Mode C does not do:** it does not mint, rotate, or recover a key. If the SC no longer has the `api_key` from the original run, Mode C is unavailable for that account — there is no registered way to obtain a fresh key for an existing sub-account (`create_or_get_sub_account_api_key` remains blocked; see `references/function-registry.md`). The honest answer in that case is that the account can still be worked in the Apollo UI, but not through this skill — do not attempt a workaround.

**Prerequisites — documented 2026-07-28.** The scripts require `jq`, `curl`, `openssl`, and `python3` (the last two only for the interactive OAuth step: PKCE challenge generation and the `localhost:3421` callback listener). Both scripts now pre-flight these and exit with a message naming what's missing, rather than failing opaquely mid-provisioning. If one is genuinely absent on the SC's machine, that's an environment fix — do not attempt to work around it by hand-crafting the API call, per the Hard Rule above.

**Who creates the sub-account: one dedicated service user — decided 2026-07-30 (Jared + Andrew 1:1), superseding the "prompt for it every run / cache it later" open item.** Every demo sub-account is created by a single dedicated Testbox identity, `tailored-demo-sub-accounts@apollo.io`, baked into `scripts/revops-provision-demo.sh` as its default. The SC is never asked for it.

**Why per-SC attribution isn't meaningfully lost:** the placeholder users this replaces gave no real audit trail either, and any *manual* change to a demo instance requires God mode, which **is** attributed to the actual person. So the identity of whoever set up a tailored demo is recoverable where it matters; only the automated creation step is pooled.

**Interim by explicit agreement, with two named revisit triggers:** if infosec raises a concern with a pooled service identity, or once TestBox provides genuine per-user identities (Andrew is setting that expectation with them, with a Salesforce-user → TestBox-user-ID mapping as the likely eventual design). Swapping this out later is a one-line change to the script's default, not a redesign.

**Formerly an open item (2026-07-27), closed 2026-07-30 by the decision above:** `revops_sandbox_master_team_user_email` is **not prompted at all**. Creation is always attributed to the service user baked into the script's default, so there is nothing to ask the SC, nothing to pass, and nothing to cache. **Corrected 2026-08-03** — this paragraph previously ended by telling you to "ask the SC each time," a leftover from the superseded prompt-every-run model that directly contradicted Step 6a and Step 6b's three-argument rule.

## Hybrid Persona Construction Procedure (added 2026-07-09)

Cross-referenced from Step 2's `configure_persona` standing rule above. This defines how every `configure_persona` payload gets built — not ad hoc, and not solely from Context Center prose.

**Why this exists:** during a live opportunity run, a manually-built persona (titles + `person_titles` only, every other field intentionally left blank rather than guessed) was compared against `generate_personas_fallback`'s output for the same company. The AI call populated `person_seniorities`, `organization_num_employees_ranges`, `organization_industry_tag_ids`, `person_locations`, and `person_department_or_subdepartments` with real, plausible Apollo taxonomy values across three suggested personas — but two of the three targeted geographies that contradicted the deal's actual APAC evidence, and employee ranges skewing enterprise that didn't match the account's own SFDC segment (SMB). Neither output alone is usable as-is: the manual persona is under-populated by design (correctly refusing to guess), the AI persona is fully populated but ungrounded in deal-specific evidence for some of its enriched fields.

This procedure exists to prevent two failure modes from recurring silently:

- **Guessing taxonomy values** — a hand-built persona will always have this gap, since nothing in the brief or Context Center payload specifies Apollo's internal enum/taxonomy values. Leaving these fields blank is safe but produces a materially weaker persona than what's achievable.
- **Blind-trusting the AI generation call** — `generate_personas_fallback` only ever receives `company_offering`/`company_name`/`company_description`. Structurally, it cannot know deal-specific facts like a region or account segment. Adopting its suggested titles, geography, or company-size filters wholesale would silently reintroduce ungrounded, deal-contradicting content into a persona — the exact thing the No-Invention Rule exists to prevent, just laundered through an AI call instead of hand-invented.

The fix is neither "guess" nor "blindly adopt": use the AI call as a taxonomy-value source, but reconcile every adopted field against the brief before accepting it, and never let it originate deal-specific facts (titles, geography, company size) that the brief itself is the source of truth for.

- **Procedure item 1.** **Always call `generate_personas_fallback` first**, using the same `company_offering`/`company_name`/`company_description` already sourced from the gate-passed Context Center payload. This is now a standard step in every `configure_persona` build, not a fallback reserved for when prose can't be mapped. Still requires the Company + Business Understanding Gate to have passed first, unchanged — there's no `company_offering` to call it with otherwise.

  **This call runs inside Step 6, after provisioning — not during Step 3's plan construction. Authoritative statement of the ordering; added 2026-07-28.** `generate_personas_fallback` is a Democles dispatch, so per Approval Gate Rule 9 it needs a real `api_key`, and since 2026-07-27 that key only exists once Step 6 has provisioned a sub-account — which happens after the main plan's Step 5 approval. So this call cannot run while the plan is still being built.

  **Why running it late costs nothing:** this endpoint does not persist anything and does not read team-scoped data — it takes `company_offering`/`company_name`/`company_description` and returns suggested taxonomy values (see `references/function-registry.md`). Its output is therefore completely independent of which instance it authenticates against, so running it after provisioning produces exactly the same harvest it would have produced earlier. **Do not read that as "it could run early against some other credential"** — there is no credential available before provisioning (the cached OAuth token is scoped to provisioning only and won't authenticate this endpoint), and inventing one is not a workaround to reach for.

  **What this means in practice.** When `configure_persona` is in scope per Step 2's standing rule, it is **Proposed**, not Blocked — the ordering is a sequencing fact, not a blocker. Draft it at Step 3 with every field the brief itself originates (titles, geography, company size — see items 3-4 below) fully populated, and disclose plainly that the AI-sourced taxonomy fields (seniority, industry tags, department codes) resolve during Step 6 and get their own approval before anything is written. Step 6 then runs the harvest, the reconciliation (items 2-6), and Touch 2 — see Workflow Step 6 for the exact sequence.

  **This is not a No-Placeholder Rule violation (Step 3), and the distinction matters.** That rule exists to stop an unresolved payload from being *dispatched* for Democles to figure out at execution time — the 2026-07-08 `configure_workflow` incident, where an unconfirmed schema was handed off as someone else's problem. Nothing of the kind happens here: the unresolved fields are resolved inside this skill's own turn, from a real API response, reconciled against the brief, and shown to the SC in full before any persisting dispatch is built. No payload containing an unresolved value ever reaches Democles. A future reader who blocks `configure_persona` by applying the No-Placeholder Rule to Step 4's disclosed-pending fields has misread both rules.

- **Procedure item 2.** **Harvest, don't adopt wholesale.** Collect the union of candidate values across every persona in `recommended_personas`, not just the first or top-ranked one. In one live test, the useful Australia/Singapore location values only appeared on the second of three suggested personas — a procedure that only inspects the first result would have missed them entirely. **Harvesting values is not the whole job when several personas come back:** if the split maps to a real structural distinction in the prospect's business, that's a choice the SC gets to make — see item 8.

- **Procedure item 3.** **Titles and functional framing always come from the brief, never from the AI.** Build `titles`/`filters.person_titles` from the Recommended Demo Flow / Context Center `customer_profile` language, exactly as already practiced. Never adopt an AI-suggested title or an AI-invented function (e.g. an unprompted "Operations Director" persona with no basis anywhere in the brief) — the AI has no deal-specific grounding to originate this from, so treating its titles as a source rather than its own generic guess would be a category error.

- **Procedure item 4.** **Geography and company-size fields are reconciled, not overridden, against known deal facts:**

  - If the brief, SFDC, or Gong evidence names a specific geography, that's the ground truth. Only adopt an AI-suggested `person_locations`/`organization_locations` value if it's consistent with (not contradicting) that evidence. If none of the harvested candidates match, don't force one in — note the gap instead.
  - Same logic for `organization_num_employees_ranges` against any known company-size signal (e.g. SFDC Account Segment). Prefer whichever harvested range across all candidate personas is closest to/consistent with the known signal; omit rather than force-fit a contradicting one.
  - If the deal has no stated geography or size signal at all, AI-suggested values may be adopted, but must be tagged `[inferred — generate_personas_fallback]`, never presented as `[verified]`.

- **Procedure item 5.** **Fields with no deal-specific evidence available at all are freely adopted from the harvested union** — `person_seniorities`, `organization_industry_tag_ids`, `person_department_or_subdepartments` — since these are exactly the fields a manually-built persona structurally cannot populate without guessing. Adopt freely provided nothing about the specific harvested value contradicts a confirmed fact elsewhere (e.g. don't adopt a `c_suite`-only seniority filter if the brief's Stakeholder Map shows the real buying committee is manager/director-level).

- **Procedure item 6.** **Tag every field's provenance in the rendered draft**, extending the existing `Source` line rather than replacing it:

  - `[deal-evidenced]` — sourced from the brief/Context Center, as today.
  - `[AI-suggested, adopted — no contradiction found]` — harvested from `generate_personas_fallback`, checked against known facts, kept.
  - `[AI-suggested, rejected — contradicts X]` — harvested but discarded, with the specific contradiction named (e.g. "rejected: targets enterprise employee counts, contradicts SFDC Account Segment: SMB").
  - `[omitted — no reconcilable source]` — genuinely nothing available, same as today's honest gap.
    This mirrors the `[verified]`/`[inferred]`/`[assumed]` discipline already used throughout the brief and Context Center payload — the same transparency principle, applied to a new composition step.

- **Procedure item 7.** **Approval stays two-touch, both touches now landing inside Workflow Step 6 — clarified 2026-07-28 (see item 1's ordering statement above):**

  - **Touch 1: the `generate_personas_fallback` call itself** (draft-only, persists nothing). Satisfied by the SC's Step 5 approval of a plan whose `configure_persona` row disclosed that this call would run — no separate ask is needed, since approving that row is approving the call it depends on. Only ask separately if `configure_persona` reached Step 6 without that disclosure having been made.
  - **Touch 2: the reconciled `configure_persona` payload**, with per-field provenance tags from item 6 shown inline, so the SC can override any specific adoption or rejection before anything is persisted. **This is a real second decision point, not a formality** — it is the moment the SC first sees the taxonomy values, so it cannot be skipped, assumed from the Step 5 approval, or folded into it retroactively.
  - **Acknowledged tension with the 2026-07-08 one-plan-one-decision consolidation (Approval Gate Rules 6-7):** for a plan containing `configure_persona`, Step 5's Approve is genuinely not the last word — Touch 2 follows. This two-touch shape predates that consolidation and is preserved deliberately, because the taxonomy values do not exist yet at Step 5 and approving a payload the SC has not seen would violate Approval Gate Rule 2 far more seriously than adding one scoped second touch does. Keep the second touch cheap and specific (show the reconciled fields, ask to confirm or adjust) rather than re-running the whole plan's approval.
  - **When the suggestion call returned a meaningful multi-persona split, Touch 2 also carries that choice — see item 8.**

- **Procedure item 8.** **A multi-persona response is a structural signal, not just a bigger value pool — surface it as an explicit choice at Touch 2. Added 2026-07-28, formalizing behavior a live run produced on its own initiative.** Item 2 tells you to harvest values across every suggested persona, which treats a multi-persona response purely as a pool to mine. That's incomplete: when `generate_personas_fallback` splits its suggestions along a real structural line — the prospect's distinct service lines, product lines, or buyer segments — the split itself is information the SC should get, because Apollo's own engine is saying this company plausibly needs several personas rather than one blended profile. Do not silently collapse that into a single persona, and do not silently expand the plan either.

  **How to handle it:**

  - **Keep the approved scope by default.** The SC approved a plan with a specific number of personas at Step 5; building more on your own initiative is exactly the scope expansion the approval gate exists to prevent. Present the reconciled payload for the approved scope as the primary path.
  - **Always offer the alternative when the split is real.** At Touch 2, alongside the confirm/adjust option, offer building the split personas instead — naming what each one would represent in the prospect's own terms (e.g. one per named service line), not as raw API output. State plainly that you kept the approved scope rather than expanding it, so the SC can see the choice was theirs to make.
  - **Only offer it when the split is genuinely structural.** Check it against the brief the same way item 4 checks geography: the distinct personas must map to something the deal's own evidence actually supports (real service lines, real segments named in the brief or the prospect's own materials). If the suggestions are just reworded variations of one buyer, or if only one of them has any basis in the deal, don't manufacture a choice — note the split in one line and proceed with the approved scope. **This is not a loophole around item 3:** the AI may surface *structure* grounded in the prospect's real business, but it still never originates titles or functional framing that the brief doesn't evidence.
  - **If the SC chooses the split,** each additional persona gets the full item 2-6 reconciliation and renders with per-field provenance tags, exactly like the first — then confirm the whole set before dispatch. This is added scope, so it needs its own look; don't dispatch N personas off a confirmation the SC gave for one. Update the plan record so Step 7's relay reports what actually ran.
  - **Use `AskUserQuestion`** for this, so the choice renders as buttons rather than as prose the SC has to answer in free text — same reasoning as the Approval Presentation Contract, applied to Touch 2.

## Handoff to Democles

Two dispatch types exist. Both go through the same Agent/Task mechanism — they differ in what they're allowed to do once there. Neither spec includes a `target_team_id` field (removed 2026-07-08, Jared's catch) — no Apollo endpoint Democles calls takes a team ID as a parameter; the API key (`api_key`) or CLI session it authenticates with determines the target entirely on its own. This skill's own target-instance rule (Approval Gate Rule 3) still governs what's shown to the SC in the approval draft — it just no longer needs to be duplicated into the dispatch spec Democles receives.

### `task_type: execute` (the normal case — now a batch of one or more approved actions)

**Consolidated 2026-07-08** — a single `execute` dispatch now carries every action the SC approved in one round (Step 5), not one dispatch per action; see Approval Gate Rule 6. The dispatch spec passed to the Democles agent must be self-contained — the agent has no access to this conversation's history, and (see the note below) no reliable way to independently locate plugin files on disk either, only what's literally in the spec. At minimum, include:

- `task_type`: `execute`
- `approved_by`: the SC's real name and timestamp of approval, covering the entire batch. Never construct or send a dispatch spec before that approval genuinely exists, and never populate this field with a placeholder or non-approval marker (e.g. `NOT APPROVED`, `pending`) — if approval hasn't happened yet, the spec itself should not exist yet. A mechanical Democles dispatch dry run (2026-07-02) confirmed this is a real risk: a spec carrying an explicit non-approval marker in this field is itself a stop condition Democles is required to refuse, not a hint it can proceed past. Applies to the whole batch — a missing or invalid `approved_by` voids every action in it, not just one.
- `api_key`: **revised 2026-07-27 — sourced from Step 6, not volunteered by the SC; amended 2026-07-28 for the reuse modes.** Whichever key Step 6 established for this plan's target: the one `scripts/revops-provision-demo.sh` just returned (Mode A), one from a sub-account provisioned earlier this session (Mode B), or an SC-supplied key that cleared every Mode C requirement. Copied verbatim into the spec. A subagent's only input is the text of its dispatch — Democles has no access to this conversation and no shared credential store to check, so if the key isn't in this field, Democles cannot get it any other way (per Claude Code's own subagent documentation: the task prompt is the entire initial context, there is no side-channel for passing data at dispatch time). Never populate this field with a placeholder — if Step 6 hasn't succeeded yet, the spec itself should not exist yet, same discipline as `approved_by`.
- `actions`: a list of one or more approved actions (one entry per row that resolved to Approve in Step 5), each with:
  - `function`: the registered function name (from `references/function-registry.md`)

  - `registry_entry`: the exact, relevant entry for this function copied verbatim from `references/function-registry.md` — endpoint or CLI command, required fields, execution surface, and any documented gotchas (e.g. the flat-body requirement for `configure_persona`/`stage_saved_search`, or the `type: "workflow"` requirement for `configure_workflow`). Copy the whole entry, not a summary of it.

    **Four things are load-bearing and get dropped most easily — check each is present before dispatching. Added 2026-07-28 after a partial copy caused a real duplicate-write incident:**

    1. **The entry's "Command/call sequence" block, in full, including any search-or-check step before the create.** A dispatch that omitted `stage_demo_sequence`'s step 1 (`apollo sequences search` before creating) removed the only pre-flight guard against a duplicate — and a duplicate then happened. Never drop these steps as preamble; they are part of the function.
    1. **Any response-shape or ID-extraction note.** These tell Democles where the new record's ID actually lives, which for several functions is not the response root. Omitting one is what turned a successful create into an apparent failure and triggered the retry.
    1. **Every documented gotcha**, including the ones that look like trivia (silent-failure fields, wrapper requirements, misleading error text).
    1. **The registry's own non-idempotency warning** applies to every create regardless of function — if the specific entry you're copying doesn't restate it, say in the spec that this create is non-idempotent and has no safe cleanup path where that's true.

    If the inlined entry is longer than feels necessary, that is the correct outcome — Democles has no access to the file, so anything you trim is simply gone. **One narrow exception, added 2026-07-09:** for a later action in the same `actions` batch whose `function` is identical to an earlier action's, you may point at that earlier action instead of re-pasting the same verbatim text (e.g. "same as action 1's `registry_entry`") — the pointer must name a specific prior action, not a vague "same as above," and only applies within this one batch, never across separate dispatches.

  - `execution_surface`: always `direct_api`. **`apollo_cli` was retired 2026-07-28 and must never be set — corrected 2026-08-03.** Every registered function is `direct_api`, and Democles refuses any spec specifying `apollo_cli` as a defect rather than running it. The reason is structural: a freshly provisioned sub-account has only an API key, and no CLI session for it exists or can exist, so a CLI command would run against whatever account the operator's local CLI happens to be logged into — by definition not the target.

  - `payload_or_command`: the exact, fully-populated content approved by the SC for this action in Step 4/5 — not a paraphrase

  - `depends_on`: **required whenever this action's `payload_or_command` contains a `${action_N.<what>}` token — added 2026-08-03.** Naming the action index and the value it needs, per Step 3's rule that the token and the declaration are required together. Democles refuses a token without a matching `depends_on`, so omitting it fails the action after approval — most often on the sequence/workflow pairing, which is the common case rather than an edge one.

  - `default_state`: where applicable (e.g. `paused`)

  - `registry_override_approved_by`: **optional, added 2026-07-08 — only for a `function` with no genuine registry entry.** A real name and timestamp, held to the same standard as the top-level `approved_by`, explicitly authorizing a call against an unregistered or unverified endpoint. Without this field, Democles refuses any action whose `registry_entry` is missing or self-narrates its own absence (e.g. "NOT IN REGISTRY"), regardless of any other instruction elsewhere in the spec — a note telling Democles to "try it and report what happens" is not sufficient on its own and was confirmed live to be correctly refused. Use this only for a genuine, deliberate decision to run an unverified call (e.g. exploratory cleanup); it is not a substitute for adding the endpoint to `references/function-registry.md` once it's actually confirmed.

A batch of exactly one action is still valid and normal — not every plan has multiple proposed actions.

**Why `registry_entry` is inlined rather than referenced, 2026-07-06 (Jared's catch).** Earlier versions of this spec (and `agents/democles.md`) pointed Democles at `references/function-registry.md` by relative path and left it to go find the file itself. That works only when Democles happens to inherit a working directory near the plugin's install location — true when this skill is invoked as a Skill (which gets an explicit base directory to resolve relative paths against), false for Democles, which is dispatched through the Agent/Task tool and has no such anchor. Its Bash tool resolves relative paths against whatever directory the outer session was launched from, which is not guaranteed to be anywhere near the plugin. A real test confirmed this: running Claude Code from a folder other than the plugin's own directory left Democles unable to find the registry file by its documented relative path, forcing it to search for it before proceeding. Inlining the entry removes the dependency on file-location guessing entirely, consistent with the "self-contained, no outside access" rule this section already states for `payload_or_command` and `api_key` — the registry lookup was the one field that quietly broke that rule.

### `task_type: verify` (interrupted or unclear outcome only)

Used only when Approval Gate Rule 8 applies — one or more prior dispatches were interrupted, killed, timed out, or their results otherwise didn't come back cleanly, and the SC needs to know whether they actually ran before deciding what to do next. This is a read-only check, never a substitute for or a shortcut around an `execute` dispatch. At minimum, include:

- `task_type`: `verify`

- `api_key`: **added 2026-07-08 — closes the gap this section used to flag.** Same field, same rule as `execute`'s `api_key` (Approval Gate Rule 9): a GET still needs to authenticate, and the spec text is Democles's only channel for it. Never dispatch a `verify` without one, exactly like `execute`.

- `checks`: a list of one or more items to check, each with:

  - `what_to_check`: plainly stated — e.g. "does a Content Center profile with this company name already exist," "does sequence X exist and what's its current state" — specific enough that Democles knows exactly what read to perform and doesn't have to infer scope
  - `function` and `registry_entry` (both recommended when known): the registered function name and its exact registry entry copied verbatim from `references/function-registry.md`, same as for `execute`. Giving Democles the actual entry — not just the function name — lets it use the documented read/search method for that object directly, without opening the registry file itself (which it has no reliable path to — see the note under `execute` above). A bare function name without the entry text still leaves Democles guessing at the read method.
  - `related_prior_dispatch`: whatever's known about the interrupted dispatch this is following up on (approximate time, what was being attempted), so Democles's report can be tied back to it

  A single `verify` dispatch should cover every action left unresolved by the same interruption — e.g. if five `execute` dispatches were killed in the same batch, that's one `verify` dispatch with five `checks`, not five separate dispatches. Reads are low-risk and cheap to batch; forcing one dispatch per check is the kind of narrow scoping that makes this capability painful to actually use in the situation it exists for.

- `execution_surface` is deliberately not required per check — **and since `apollo_cli`'s retirement on 2026-07-28 there is nothing left to choose between, corrected 2026-08-03.** Every read is `direct_api`, scoped by the spec's `api_key`. The field is omitted here because it is invariant, not because Democles picks it: the earlier framing of this as "Democles's call, guided by the inlined `registry_entry`" described a two-surface world that no longer exists, and left this contract authorizing a surface Democles is required to refuse.

No `approved_by` or `payload_or_command` is required for a `verify` dispatch, since nothing is being written — but `api_key` is still required (see above), and the same explicit trigger discipline as `execute` applies: only dispatch one when Rule 8's condition genuinely applies, not as a routine double-check.

**Known blind spot: personas have no list/index endpoint reachable via API key** (per the function registry's Authentication/hosts section — the only discovery path found so far is a browser-session field, not available to Democles). A `verify` check against a persona will typically come back `inconclusive` for this structural reason, not because the check was done poorly. Don't read `inconclusive` as evidence either way, and don't retry the same check expecting a different answer — relay it to the SC as a real gap that may need a manual UI check instead.

Dispatch through the Agent/Task tool, using the spec as the agent's entire task prompt. Do not give the agent any instruction beyond "execute exactly this approved spec and report the result" (for `execute`) or "check exactly these items and report the result for each" (for `verify`) — it should have no room to interpret, expand, or improvise. See `agents/democles.md` for what the agent does with each dispatch type and what it returns.

**Relaying a `verify` result.** Unlike an `execute` result, a `verify` result isn't something to approve — it's information the SC needs before deciding what to do next. When the dispatch covered several checks, relay them together as one short table (one row per check) rather than as separate messages — the SC is trying to get oriented after an interruption, not work through another approval loop. For each check, route based on Democles's answer:

- **`check_status: error`** → the read itself failed (credential/network/endpoint issue) — tell the SC plainly that this one couldn't be checked at all, and why, rather than folding it into "inconclusive." Don't guess at the outcome from an error.
- **`found: true`** → already done — mark it resolved without re-dispatching.
- **`found: false`** → treat it as a fresh "Proposed below" row and re-enter the normal Step 3 loop for it.
- **`found: inconclusive`** → tell the SC plainly, including Democles's stated reason (e.g. "personas have no list endpoint"), and ask how they want to proceed — check the UI directly, or approve a fresh `execute` and knowingly accept the small risk of a duplicate. Never silently assume either outcome on the SC's behalf.

## Approval Gate Rules (Hard)

These override any default that would skip or compress approval:

- **Approval Gate Rule 1 — No plan executes without a rendered draft and an explicit SC approval for that specific draft.** Standing or implied approval from a prior action does not count.
- **Approval Gate Rule 2 — The draft shown to the SC must contain the literal content that will be sent — never a summary — and must state what it was built from.** If the SC can't see every field/value the action will write, they can't actually approve it; if they can't see what Layer 1 source drove it, they can only rubber-stamp it, not evaluate it. **Reconciled 2026-07-16 with the terse-by-default rule in Step 4 (two passes):**
  - *Reasoning:* one short, plain-language phrase by default — a quick note on where it came from, not a formal citation and not a justification for the choice — with full detail available on request. Terser presentation, not a weaker approval: a line that's short because it's a quick note is compliant, short because it's vague is not.
  - *Payload:* renders as plain field: value lines instead of a raw JSON code block — a syntax simplification, not a summary, and not itself a loosening of this rule. **Revised 2026-07-16 (Jared's directive, third pass) — a real, scoped loosening on top of that:** only the fields judged high-signal for that action render by default (see Step 4 for what qualifies); the rest collapse to a count, with the exact raw payload — every field, nothing dropped — always available on request before dispatch. This is a deliberate exception to "never a summary," not a reinterpretation of it: a wrong value sitting in a collapsed field won't get caught unless the SC asks, which is exactly why the high/low-signal judgment call has to be conservative (default to showing a field, not collapsing it, whenever it's unclear) and why every collapsed line names what's behind it rather than just a bare count.
  - *Execution surface* is the one thing genuinely dropped from the rendered draft, not just compressed — it's a Democles routing detail the SC isn't evaluating, and it still reaches Democles via the dispatch spec regardless.
  - *One action resolves part of its payload after this draft, by design — added 2026-07-28.* `configure_persona`'s AI-sourced taxonomy fields don't exist yet at render time (see the Hybrid Persona Construction Procedure's item 1). This rule is still satisfied, just across two touches instead of one: the draft discloses which fields are pending and why, and Step 6(e)'s Touch 2 shows the SC every literal value before anything is persisted. What this rule forbids — approving a write the SC hasn't actually seen — never happens.
- **Approval Gate Rule 3 — The target instance is a demo sub-account this skill provisioned — freshly, by default, or a prior one only on the SC's explicit request. Never a hardcoded value, never inferred from context, and never production.** **Revised 2026-07-27 (replacing the SC-supplied-key model), amended 2026-07-28 to admit the reuse branch.** The default remains fresh provisioning in Step 6, and that default is what makes this rule strong: an account created seconds ago under the fixed RevOps parent cannot be a production team. **Mode C (cross-session reuse) is a deliberate, named exception that partially gives that property up** — a supplied key is unverifiable, by this skill and by Democles alike — so it carries mandatory procedural guardrails (explicit request, Team ID plus key, explicit SC attestation that it is not production, target stated in the rendered plan, refuse on any doubt). See `Reuse Mode (Mode C) — Requirements and Limits`. **The refusal obligation is unchanged in every mode:** if the SC asks for or implies production, a customer instance, or any target that isn't a demo sub-account this skill provisioned, refuse and say why. Whether the Team ID appears in the rendered plan is now mode-dependent (Step 4's targeting rule): omitted in fresh-provisioning mode, where it doesn't exist yet and the SC sees it at Step 6; stated prominently in Mode C, where naming the pre-existing target is a genuine disclosure rather than a redundant echo.
- **Approval Gate Rule 4 — Anything that could run on its own is staged inert by default — sequences `paused`, workflows `active: false`.** Only stage as `active` if the SC explicitly says so in the same approval turn — never as a default and never inferred from enthusiasm ("this looks great, let's send it") without the literal word active/live/send. **Extended 2026-07-28 to name workflows explicitly:** `configure_workflow`'s `active: false` was previously only stated in Step 3 and the function registry, leaving this rule reading as sequence-only when the underlying principle covers both. `approval_type: "manual"` (Step 3) is a separate, additional safeguard on workflows and is never a substitute for `active: false`.
- **Approval Gate Rule 5 — This skill never calls Apollo itself for any of the plan's own actions — only Democles executes those.** **Narrowed 2026-07-27:** the one exception is Workflow Step 6's sub-account provisioning, which is not a plan action at all and runs through exactly two bundled scripts, never a general-purpose Apollo call. If asked to "just do it" for any registered function without going through Democles, decline and explain that execution is a separate, scoped step — this keeps the approval gate meaningful rather than decorative. The same refusal applies if asked to use Step 6's Bash access for anything beyond provisioning.
- **Approval Gate Rule 6 — Proposed actions are shown together as one consolidated plan, and approved or discussed as a whole.** *(Superseded 2026-07-08 — this rule previously mandated one-at-a-time; see below.)* When the Step 2 mapping table has more than one "Proposed below" row, render every action's full draft in a single consolidated message (Step 4), then resolve the whole plan through one round of SC response (Step 5). Andrew and Jared decided 2026-07-08 to consolidate into one recommendation and one Democles sub-agent run, since walking each action individually required the SC's continuous attention for the full run. What actually protects this gate is unchanged: every literal payload and its reasoning must still be shown before anything is approved — the number of messages it takes to get there was never itself the safety property.
- **Approval Gate Rule 7 — The SC's response is binary, gathered via `AskUserQuestion` per the Approval Presentation Contract below** — **Approve** (send the plan to Democles exactly as shown) or **something's off** (open a discussion before anything is sent). *(Simplified 2026-07-08 — an earlier draft of this rule added a three-button Approve/Decline/Revise choice plus a structured per-action breakdown grammar; Jared decided that's more structure than an SC actually needs — a plan either looks right and goes, or it doesn't and gets talked through.)* There is no separate Decline button and no per-action breakdown syntax to parse — if only part of the plan is wrong, that comes out through the discussion, not through the SC composing a structured reply. Treat anything that isn't a clear Approve as "something's off" and start the conversation.
- **Approval Gate Rule 8 — If a dispatch is interrupted or its outcome is unclear — including a kill, timeout, or any other break mid-execution — resolve that uncertainty by dispatching a read-only Democles verification task (`task_type: verify`, see `Handoff to Democles`) or by asking the SC directly. Never resolve it with a direct tool call to Apollo made by this skill or by the orchestrating assistant itself, not even a "quick" read-only check.** This applies with no exception for how low-risk the check seems — a read is still a direct call this skill is not authorized to make, per Rule 5 and the Operating Boundaries below. Real incident, 2026-07-06: after several Democles dispatches were killed mid-flight, the orchestrating assistant reached for a direct `curl` to check what had actually written, which is exactly the bypass this rule exists to prevent — caught only because the permission prompt happened to reveal the call was originating outside a sub-agent. Do not rely on catching it after the fact; the rule is what prevents it from happening at all.
- **Approval Gate Rule 9 — Never dispatch Democles — `execute` or `verify`, no exception — without a real `api_key` for an established target. Period.** **Revised 2026-07-27 (replacing the SC-supplied-key model), clarified and amended 2026-07-28.** The key must come from one of Step 6's three modes: this plan's own fresh provisioning call (Mode A), a sub-account provisioned earlier in this same session (Mode B), or an SC-supplied key that has passed every Mode C requirement including the attestation (Mode C — see `Reuse Mode (Mode C) — Requirements and Limits`). **Outside those three, a volunteered key is still refused** — an SC pasting a key without going through Mode C's requirements does not satisfy this gate.
  - **Precise ordering, corrected 2026-07-28:** the precondition is that **Step 6(c) has returned a key** (or Mode B/C has supplied one) — not that all of Step 6 has finished. Step 6(e)'s `generate_personas_fallback` dispatch legitimately runs *inside* Step 6, after (c) and before (f); reading this rule as "all of Step 6 must complete first" recreates a circular dependency that doesn't exist (see the Hybrid Persona Construction Procedure's item 1).
  - **`approved_by` for the Step 6(e) generation dispatch, specified 2026-07-28:** use the SC's Step 5 plan approval — that approval covered a plan whose `configure_persona` row disclosed this call would run, which is Touch 1 (Procedure item 7). Do not stall for a separate approval, and do not populate it with a placeholder; if that disclosure never happened, ask the SC directly instead of inventing a value.
  - For a `verify` dispatch (Approval Gate Rule 8), reuse the key for that plan's own established target — never a different account. **If provisioning itself failed ambiguously and no key was ever returned, `verify` is unavailable** and the fallback is a manual UI check (see Step 6(d)); that's a real, documented limitation, not a reason to substitute some other credential.
  - Never populate `api_key` with a placeholder. A `verify` dispatch reads rather than writes, but a read still needs to authenticate — "it's just a read" is not an exception to this rule.

## Approval Presentation Contract (interactive plan approval)

**Added 2026-07-08** — live testing on 2026-07-07 found the Approve/Decline/Revise prompt rendering inconsistently (sometimes a real selectable widget, sometimes plain text the SC had to type back), traced to this skill never actually invoking a button-rendering tool despite asking for a bounded response. This contract borrows `demo-prep-intelligence`'s proven Menu Presentation Contract pattern rather than reinventing one.

This contract governs how the consolidated plan (Step 4) is presented for approval. It is a presentation rule, not a routing rule — it does not change what the SC can approve or push back on, only how the choice is gathered.

**Runtime.** This skill runs in Claude / Claude Code. The interactive mechanism is Claude's **`AskUserQuestion`** tool, which renders each option as a clickable button. `AskUserQuestion` is declared in this skill's `allowed-tools` frontmatter so it is available at the approval gate.

**Rule (hard STOP pattern).** After rendering the consolidated plan in Step 4, the agent MUST:

1. Render the plan content (every action's full draft, `Source` line) — nothing about this changes.
1. **STOP.**
1. Call the **`AskUserQuestion`** tool with the plan's two approval options.
1. **Do NOT proceed to Step 6 (establishing the target and dispatching), and do NOT continue the response, until the SC responds.** Nothing gets provisioned before this answer either — that's the whole reason provisioning sits in Step 6.

The agent MUST NOT print "Respond with Approve / something's off" as literal Markdown text for the SC to type back, and MUST NOT pick an option on the SC's behalf and keep going.

**How to invoke `AskUserQuestion`.** Call it with:

- a `question` that names what approving actually sets in motion — **expanded 2026-07-28 so account creation isn't a surprise at the Step 6 prompt.** In fresh-provisioning mode: e.g. *"The plan above has N action(s), and approving also creates a new Apollo sub-account for the prospect to run them against. Ready to go?"* In Mode C: name the existing target instead, e.g. *"The plan above has N action(s), all written to the existing sub-account [Team ID]. Ready to go?"* Keep it one sentence — this is a disclosure, not a second explanation of the plan.
- a short `header` chip, e.g. `Approve plan`
- two options — **simplified 2026-07-08** (an earlier draft of this contract had three buttons plus a free-text per-action breakdown; Jared decided a plan either looks right and goes, or it doesn't and gets talked through — nothing in between needs its own button):
  - **Approve, send to Democles** — "Run every action in the plan exactly as shown"
  - **Something's off, let's discuss** — "Don't send anything yet — I want to talk through a change first"

If the SC picks the second option, follow Workflow Step 5's discussion path (ask what's wrong, apply the fix — which may mean changing a payload, dropping an action, or abandoning the plan — then loop back to Step 4 with a fresh consolidated draft and a fresh `AskUserQuestion` call). There's no structured per-action reply syntax to parse; whatever comes out of that conversation is applied directly.

**Fallback (plain-terminal surfaces only).** Some Claude surfaces may not render `AskUserQuestion` as buttons. The agent should still CALL `AskUserQuestion` — the host degrades it to a text selection prompt on its own. Only if the tool is genuinely unavailable in the running surface may the agent fall back to a bounded, numbered menu and say `Interactive approval unavailable here — reply Approve, or tell me what's off.` A Markdown option list printed **without** an `AskUserQuestion` call, while the tool was available, is the defect this contract exists to prevent — it is exactly what item 12 found happening inconsistently before this fix.

**Unchanged boundaries.** This contract changes presentation only. It does not authorize dispatching without approval, and every Approval Gate Rule above (literal payload, correct-targeting refusal, paused default) still applies in full.

## Operating Boundaries

- **Three input channels for Layer 1's output, plus the SC's approval decision, nothing else**: the `demo-prep-scratchpad.md` handoff file (preferred, checked first), same-session conversation context (checked regardless, for updates on top of the scratchpad), and manually pasted output (fallback only). No independent Salesforce, Slack, or Gong research — that's demo-prep-intelligence's job.
- **Filesystem access is limited to two things: reading the scratchpad, and running the two bundled provisioning scripts (Step 6).** It does not write to the scratchpad and does not write anywhere else. Reading the scratchpad is not execution capability; running the two scripts is, and it's the one scoped exception — see the bullets below.
- **No execution capability against any registered configuration function, and no exception for reads.** This skill has no way to write or read any of the plan's own actions (Context Center, personas, workflows, saved searches, sequences) — that stays exclusively Democles's job, including read-only checks after an interrupted or ambiguous dispatch (a `verify` dispatch) or the SC's own confirmation, never this skill's own tool call. See Approval Gate Rule 8.
- **One scoped exception, added 2026-07-27: Bash access limited to `scripts/revops-oauth-login.sh` and `scripts/revops-provision-demo.sh`, for Workflow Step 6 only.** This is the sole thing this skill's `allowed-tools: Bash` grant may be used for — see `Provisioning the Demo Sub-Account` and its Hard Rule. Using Bash for anything else (a direct Apollo API call, a registered function's action, or any command not part of Step 6) is out of bounds, no different from the boundary that existed before this exception was added.
- **`Read` in `allowed-tools` is not a new capability — added 2026-07-31.** It pre-approves reading this skill's own bundled reference files (`references/function-registry.md`) without prompting the SC mid-run. Per Claude Code's skills documentation, `allowed-tools` is a permission pre-grant for the turn that invokes the skill, not an allowlist — it grants nothing this skill could not already do and removes nothing. It does **not** widen the Bash exception above, and it is not license to read arbitrary local files: this skill reads its own references and the Layer 1 scratchpad handoff, nothing else.
- **No persistent memory of prior approvals.** Every plan is approved on its own.
- **Functions not in the registry's live set** are never simulated or faked as if they ran — always route them to the roadmap note instead. (Sub-account creation is no longer in this category — see Workflow Step 6 — but sub-account API-key minting as a standalone action, independent of creating a new account, still is.)

## Non-Goals

- Does not configure Apollo itself for any of the plan's own actions — Personas, workflows, saved searches, sequences, Context Center changes, and the persona-generation call are live, registered functions (`configure_persona`, `configure_workflow`, `stage_saved_search`, `stage_demo_sequence`, `push_context_center_profile`/`push_context_center_product`, `generate_personas_fallback`) that stay exclusively Democles's job — see `references/function-registry.md`. Provisioning the sub-account itself (Workflow Step 6) is the one exception, and is scoped to exactly two bundled scripts, never a general Apollo API/CLI capability.
- Does not target production or any customer-facing instance, ever. Every plan runs against a demo sub-account this skill provisioned — a fresh one by default, or a prior one only under Mode C's explicit-request-plus-attestation requirements (see `Reuse Mode (Mode C) — Requirements and Limits`).
- Does not delete, rotate, or recover anything it created. No deletion function is registered, and there's no way to mint a replacement key for an existing sub-account — cleanup and UI-side account management stay manual (see Workflow Step 9).
- Does not replace demo-prep-intelligence's research, or Democles's execution — this skill is strictly the approval gate in between, plus the one narrow provisioning step immediately before dispatch.
