## SC-Facing Output Rules (Hard)

These rules govern what the SC sees by default. They override any earlier convention in this file that might suggest emitting raw machine-readable state to the SC.

1. **Never show internal router YAML, orchestration state, pipeline traces, or reasoning chains as the default visible output.** YAML, router payloads, pipeline-stage logs, and intermediate state may exist internally to drive routing and composition, but they must not be the primary artifact rendered to the SC.
1. **The visible output must be human-facing.** The first thing the SC sees for any flow must be either (a) a short intake summary plus one or more directly usable artifacts (copyable message, AE-sync questions, brief, walkthrough), or (b) a prompt for the missing input the skill needs to proceed. **Exception: `SKILL.md`'s Step Zero explicit-demo-configuration-intent door.** When the SC's phrasing already names demo-instance configuration as the goal (e.g. "create a tailored demo instance"), Step Zero produces the seven-section brief directly as the first visible output, with no preceding intake summary — asking first would itself be the wasted turn Step Zero exists to remove. This exception is scoped to that one door; Step Zero's ambiguous-intent door still satisfies (b) via its `AskUserQuestion` prompt, and every other flow in this skill still requires (a) or (b) in full.
1. **The router selects the next move; it is not the message.** Treat the router as an internal control that picks AE sync questions vs. analyze evidence vs. build brief. Never present the router's selection as the primary deliverable.
1. **Diagnostics are opt-in.** If the SC explicitly asks "why did you pick this path", "show your reasoning", "show the router", or "show the YAML", the skill may emit a compact "Why this route" summary (3–6 lines, plain English). Only emit raw YAML, raw pipeline trace, or machine-readable router state when the SC explicitly asks for machine-readable, debug, or diagnostic output.
1. **Action-surface first.** For any flow that produces an outbound message (AE sync ask, dealroom coordination, internal escalation, customer-facing follow-up), the primary artifact must be a clean, copyable message the SC can paste, plus a small action menu — not the upstream reasoning that produced it.

**Allowed artifact class — Visible Gate Block.** A rendered, human-facing Visible Gate Block
(plain-English checklist of what was checked, pass/fail per criterion with source + confidence,
and what happens next / what is blocked) is an ALLOWED SC-facing artifact and is NOT the
forbidden machine-readable state described in rule 1. It is a human-facing summary, not raw
router/pipeline state. See `SKILL.md` → Visible Gate Block primitive.

## Outbound Messaging Pipeline (Mandatory)

Every outbound message generated by this skill — AE sync ask, dealroom post, Slack DM, internal escalation, internal coordination draft, customer-facing follow-up — must be composed through this skill's own six-stage composition discipline before it is shown or queued.

Operational sequence applied internally to every outbound message:

1. **Parse state** — extract entities, attendees, stage, deal motion, calendar/email signals, prior promises.
1. **Filter / ground claims** — drop unsupported certainty, mark inferred vs. verified, never assert what the source data does not support.
1. **Map constraints** — read-only boundary, no-send-without-approval, audience constraint, do-not-promise constraint, dealroom destination rules.
1. **Route action** — choose AE DM vs. dealroom post vs. AE-sync question set vs. handoff to deal-execution.
1. **Compose** — draft the message for its audience: internal coordination, AE-sync asks, and internal escalations use a direct internal voice; customer-facing follow-up and prospect-facing language use a sales-appropriate voice.
1. **Humanize / compress** — polish the draft for voice, compress for length, and remove AI-sounding patterns before it reaches the SC.

Rules:

- This pipeline runs internally. Do not expose the pipeline trace, stage labels, or intermediate drafts unless the SC explicitly asks for diagnostics.
- The pipeline applies to drafts only. This skill remains read-only — composing through the pipeline does not authorize sending.
- The SC sees the final composed, humanized draft. The router payload, pipeline state, and intermediate drafts stay internal.

## Read-only Operating Boundaries (Inviolate)

- **One input**: a deal identifier — account name, SFDC opportunity name, or Slack dealroom/channel name.
- **Canonical outputs**: either a structured seven-section demo prep brief or the five-part synthesis package, selected by the user's ask. Lifecycle outputs such as Assigned Opp Intake, AE Sync Prep, refresh summaries, debrief prep, and trial planning extend from that contract without replacing the seven-section brief.
- **Read-only**: never write to Salesforce, Slack, Gong, Glean, Notion, email, CRM, the Apollo product, or any real business system while executing this skill. The single, narrow exception is the session-scratchpad handoff file defined in the next bullet - every other system named in this rule remains absolute, with no further exceptions.
  - **What "write" means here, stated precisely - added 2026-07-28 (David Johnson's call, as skill author).** This rule prohibits *this skill calling a write tool*. It does not prohibit composing content that a human or another skill may later post. Concretely: this skill **never calls** `slack_create_canvas`, `slack_update_canvas`, `slack_send_message`, `slack_send_message_draft`, or any other Slack write tool - not with approval, not per-artifact, not ever. What it may do is compose a Slack Canvas deal room or a dealroom/AE message **as copyable content**, which the SC posts themselves or delegates to `deal-execution`. That delegation is `deal-execution`'s write under `deal-execution`'s own approval gate, not this skill's.
  - **Why this needed saying.** A full-file audit (2026-07-28) found that `SKILL.md` and `references/canvas-generation.md` had built a Slack Canvas *creation* path - classifying `slack_create_canvas` as an approved write action - which this rule flatly forbade. Because this file governs on conflict, that whole path was canonically unauthorized while being documented as a feature. David reframed it as delegate-only, which resolves the conflict and, as he noted, conserves tokens on larger deals since the skill no longer carries write-orchestration mechanics. **Recording the boundary here rather than leaving it implicit is the actual fix** - otherwise the next reader re-derives the same contradiction.
- **Session-scratchpad handoff exception (added 2026-07-06, approved by David Johnson, skill owner):** this skill must write exactly one handoff file per run to a session-local scratchpad location, and nowhere else - triggered automatically by the Terminal Output Assertion's condition (c) in `SKILL.md` every time a brief, synthesis package, or Context Center payload renders. This is a mandatory step, not a discretionary permission. This exists solely to let `demo-instance-configuration` reliably consume this skill's structured output even if the conversation compacts or restarts between the two skills running - it does not relax any other boundary in this section. Rules for this exception:
  - The scratchpad location is never a git-tracked path, never a location delivered to or visible to the SC as a deliverable, and never any external system - not Salesforce, Slack, Gong, Glean, Notion, email, CRM, or the Apollo product.
  - Concrete convention: the file is named `demo-prep-scratchpad.md` and lives in the runtime's ephemeral working/temporary directory - never this plugin's own source/deliverable folder, never any path tracked in git. `demo-instance-configuration` checks this exact name and location on every run, so do not rename it or write it elsewhere.
  - The file contains only the current seven-section brief and/or Context Center payload, with every `[verified]`/`[inferred]`/`[assumed]` source and confidence tag intact and unmodified - no new claims, no summarization that drops tags.
  - The file is overwritten on every run. It is never appended to or accumulated across runs.
  - **Clarified 2026-07-28 — "per run" means per *deal working session*, not per rendered artifact.** The Terminal Output Assertion's condition (c) fires on each major artifact (brief, synthesis package, Context Center payload), and a session commonly renders more than one for the same deal — a brief first, then a Context Center payload. Those must **accumulate into one file for that deal**: writing the Context Center payload must not erase the brief already written for the same deal in the same session, since `demo-instance-configuration` may need both. Overwrite means starting clean when the deal changes or a fresh run begins for the same deal — never discarding a sibling artifact from the run in progress.
  - The file is never the primary SC-facing output by default - the SC-facing output remains the rendered brief/payload per the SC-Facing Output Rules above. One conditional exception: if the SC indicates `demo-instance-configuration` will run in a separate or fresh session rather than continuing now, this skill must proactively offer to show the scratchpad's exact content as copyable text so the SC can save it themselves - the scratchpad file itself is not guaranteed to persist once this session ends, so this is the only reliable way to carry the handoff across a session boundary. See `SKILL.md`'s "Handoff to demo-instance-configuration" section for the full flow. This exception exists solely for that specific circumstance - it is not a standing invitation to reveal the scratchpad at will.
  - This exception authorizes nothing beyond the single handoff file described here. If there is any doubt whether a write target qualifies as "the session scratchpad," treat it as out of bounds and do not write.
- **Calendar/email read-only**: when Gmail with Calendar is connected, the skill may search calendar events and email threads to align meeting context, attendees, agenda, and recent customer/AE communications. It must never draft, send, update, RSVP, reschedule, or modify calendar/email from this skill.
- **Internal coordination drafts allowed**: the skill may generate copy-paste draft text for AE sync requests or active dealroom coordination, but it must label the text as a draft and never send, post, schedule, route, or update anything.
- **No customer-facing outreach, routing, pipeline updates, or execution.**
- **Canonical rebuilds are full rebuilds**: when the skill queries source systems, rebuild the brief from currently available data rather than silently patching an old artifact.
- **Contextual refreshes are allowed inside the current conversation**: when the SC provides new call notes, Slack excerpts, data test results, or attendee changes, merge that user-provided context into the current brief with explicit source labels and a short change summary. This is not persistent storage and does not replace a source-backed full rebuild. Layer-2/Layer-3 consumers must always be passed a brief whose user-provided claims are source-labeled (`Source: User-provided ...`) and confidence-tagged so downstream skills can decide whether to trust them.
- **Never hallucinate.** Unknown is better than confidently wrong.
