### Resolving person properties (Account Owner, GTME)

`Account Owner` and `GTME` are Notion `person` properties, which need a Notion
user reference, not a plain name string:

1. Get the name from Salesforce (GTME owner field) and/or the user's own input
   (who the AM is).
2. Call `notion-search` with `query_type: "user"` and the person's name or
   email to find their Notion user.
3. If found, pass their user URL (or `user://<id>`) in an array as the
   property value, e.g. `"Account Owner": ["user://<id>"]`.
4. If no confident match is found, **skip setting the property** rather than
   guessing, and note in the page content ("AM: <name>, GTME: <name> — could
   not resolve to a Notion user").

## Checking for an existing page first (Step 1a)

Before creating, check whether this account already has a page here, so the
skill can decide update-vs-create itself instead of asking the user:

1. Call `notion-search` with `data_source_url:
   "collection://3b4ab2b3-b496-80b4-9eb6-000befa12a27"` and the account's
   Salesforce ID as the query first (most precise), falling back to the
   account name if that returns nothing.
2. If a page comes back for this account, `notion-fetch` it to confirm it's
   really the same account (matching Salesforce ID), then use
   `notion-update-page` (`replace_content` for the body, `update_properties`
   for the properties) instead of `notion-create-pages`. Preserve the page's
   existing icon/title unless they're wrong.
3. If nothing matches, proceed to `notion-create-pages` as below.

Skip this check entirely if the user's request explicitly asked for a new/
duplicate/test page — go straight to create in that case.

## Page metadata

- **Icon:** use `🧭` (compass emoji) to match the existing convention in this
  database.
- **Title:** the account name only (e.g. `EBANX`), not a longer "Account Plan
  — X" string — the database itself provides that context.

## Content template

Write the page body in Notion-flavored Markdown (see the
`notion://docs/enhanced-markdown-spec` resource for exact syntax — tables,
callouts, colors, etc. all use that spec, not plain HTML). Follow this section
structure, which mirrors the established format already in use in this
database:

```
> Account plan for {{Account Name}}, generated by the accountplan skill.
> AM/Account Owner: {{name}}. GTME: {{name}}.
---
# 1. Current State
**Feature Usage** — table of Apollo feature areas (Prospecting, Sequences,
Email, CRM, Enrichment, Dialer, AI, Lists, Meetings, Workflows, MCP) each with
a 🟢/🟡/🔴 status cell (color the cell green_bg/yellow_bg/red_bg) and a dated,
sourced note. Say plainly when a feature has no confident signal rather than
guessing.
**Facts** — a metric/detail table: Adoption Snapshot, Renewal Risk (with a
colored dot: green/orange/red as text via <span color="...">●</span>),
Metric 1, Metric 2, Known Competitors — each cited to its source with a date.
**Seat Whitespace Opportunity** — licensed seats vs. sales-org headcount from
Apollo enrichment, with the resulting whitespace number.
**Apollo Proof Point** — an account-specific proof point if one exists;
otherwise general Apollo benchmarks, clearly labeled as not account-specific.
---
# 2. What's Happening in Their Business?
### 2a. Who does this account sell to, and what signals would they care about?
Table: Audience & Segments | Buyer Personas | Their ICP in Apollo Terms |
Buying-Intent Signals to Monitor | Target-List & Personalization Play.
### 2b. What's happening in their business? (change story & signals)
Dated table of business developments (funding, expansion, exec moves, product
launches, etc.), most relevant first. Close with a `<callout icon="⏱️"
color="yellow_bg">` block naming the "Why now" trigger.
---
# 3. Value Hypothesis
A table of 2–3 value pillars (Pillar | Value Hypothesis), each grounded in a
business signal from section 2 and an Apollo capability from
`apollo-value-props.md`.
---
# 4. Stakeholder Map
State the minimum-bar coverage target for the account's segment and whether
it's met. Then the stakeholder table: Name | Title/Function | Role in Deal |
Sentiment | Engaged? | Exec Aligned? — color each Sentiment/Engaged?/Exec
Aligned? cell per the legend in SKILL.md ("Formatting the stakeholder table").
**Every Name cell must be a `[Name](linkedin-url)` link** per the mandatory
"LinkedIn links" rule in SKILL.md's stakeholder map spec — never leave a name
unlinked without an explicit `*(LinkedIn not found)*` note. Add a one-line
color legend, a "Notes on this roster" callout for inferred/uncertain matches,
and a "Gaps" list.
---
# 5. Key Actions We Want To Take
**Always** an empty Action | Owner | Target Date table (headers only, no
filled rows) with a `*[To be completed by the account manager.]*` note above
it — see "'Key Actions We Want To Take' is always blank" in SKILL.md. Do not
fill this in even if the user supplied candidate actions elsewhere in the
conversation; put those in the Milestone Plan instead.
---
# 6. 30–60 Day Milestone Plan
Milestone | Owner | Target Date | Expected Outcome table, then 1–2 sample
outbound messages (AM → customer) as `<callout icon="✉️" color="blue_bg">`
blocks, marked illustrative per the guardrail in SKILL.md. Do not add a
separate "Next Immediate Actions" table — the Milestone Plan table already
carries near-term items; a duplicate summary table is redundant.
---
**Appendix — Sources**
Bullet list of which systems were queried (with dates) and which were not
queried this session, per source: Salesforce, Snowflake, Apollo MCP, Slack,
web research, transcripts, Glean.
```

Keep the same honesty guardrails as the rest of this skill: cite every claim,
mark inferences and low-confidence matches explicitly, and say "no confident
signal found" rather than inventing content for any subsection.
